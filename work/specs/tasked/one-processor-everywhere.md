## Problem Statement

A processor written for the in-browser path cannot run on the server, and vice versa. The two authoring APIs already look almost identical on purpose (`on<EventName>(state, event, config)` in both), but the state argument differs: `@etherfold/js-processor` hands the author an immer draft of a free-form object, while `@etherfold/processor-sqlite` hands them a `MutationContext` over declared entities. A handler body is therefore not portable, so the same indexing logic gets written twice, and the two copies drift.

That split also blocks the query layer. A generic query surface (and the GraphQL frontend already researched and measured) can only be generated from a declared schema. The free-form object path has no schema to generate from, so any query capability built on entity declarations would be available on the server and absent in the browser, which is the opposite of what this project claims: indexing anywhere.

Underneath both is an unstated assumption worth making explicit: how much history the state keeps. Reorg revert already forces a floor, because undoing a reorg means reopening entity versions closed at the fork point, so a store must retain superseded versions back to the finality depth whether or not anyone calls it history. Today that retention is implicit and differs by backend, which means "can I query this at block N" has no answer a caller can rely on.

## Solution

One authoring API, several storage backends behind one seam, with retention as an explicit, declared capability rather than an emergent property of whichever backend happened to be wired in.

An author writes a processor once: entity declarations plus `on<EventName>` handlers that read and write through a `MutationContext`. Where that state physically lives (SQLite on a server, SQLite compiled to wasm in a browser, or a patch-based light store) is a deployment choice that the processor does not see and does not encode.

Retention becomes a number the deployment sets and the backend reports: the finality depth as the floor (which costs nothing extra, since reorg safety already demands it), some window of N blocks, or unbounded for full time travel. A consumer asking for state as of an old block gets either an answer or an explicit refusal, never a tip read dressed up as a historical one.

## User Stories

1. As a processor author, I want to write my indexing logic once, so that the same processor runs in a browser tab and on a server without a second implementation.
2. As a processor author, I want to declare my entities as `{name, id, fields}`, so that the storage layer owns the DDL, the versioning and the reorg revert rather than each processor reimplementing them.
3. As a processor author, I want to write a whole row with `set` and a partial change with `update`, so that the common counter-increment case is one line while the storage model (a version is a complete row) stays visible.
4. As a processor author, I want my handlers to be uniformly async, so that one signature works whether a read hits memory or a database.
5. As a processor author, I want read-your-writes within the block being processed, so that two events in the same block that touch one counter compose correctly.
6. As an application developer, I want to choose a storage backend for the browser, so that I can trade payload size against query capability for my own app rather than accepting one project-wide answer.
7. As an application developer, I want the backend to tell me what retention it provides, so that I can discover at startup whether historical queries are available instead of discovering it from a wrong answer in production.
8. As an application developer, I want a query surface generated from the same entity declarations that drive storage, so that I do not hand-write and hand-maintain a second description of my data.
9. As an application developer, I want historical queries to be refused explicitly when the backend cannot serve them, so that a missing capability is a clear error rather than a silently-wrong number.
10. As an operator, I want to set the retention window, so that a server can keep full history while a browser keeps only what reorg safety requires.
11. As an operator, I want retention to be enforced by pruning, so that storage does not grow without bound on a long-running server that does not need time travel.
12. As an operator, I want the same processor and the same entity declarations whether I run the single-process CLI or a split watcher and indexer-server, so that scaling out is a deployment change and not a rewrite.
13. As a maintainer, I want the subtle code (versioned rows, as-of reads, revert) to exist once per backend and be covered by one shared conformance suite, so that two backends cannot drift into answering the same question differently.
14. As a maintainer, I want a backend's declared capabilities to be tested, so that a backend claiming `asOf` and failing to deliver it fails a test rather than a user.

## Implementation Decisions

Settled in discussion, recorded here to seed tasking.

- **The authoring API is the `SQLProcessor` shape, generalised.** `MutationContext` (`get` / `set` / `delete`, plus `update` sugar) becomes the single write surface, and the name stops implying SQL. The direction is forced: `MutationContext` is the more constrained API, so a freer substrate can implement it, whereas backing arbitrary nested object mutation with versioned rows requires materialising the store, which `sql-backed-event-processor` already rejected.
- **Handlers are uniformly async.** The alternative, typing reads as `T | Promise<T>`, is infectious at every call site for the benefit of saving a microtask on the path where the work is dominated by log fetching.
- **`set` writes a whole row; `update(entity, id, partial)` is sugar over get-then-spread-then-set.** The primitive mirrors the store's close-then-insert honestly; the sugar keeps the counter case readable.
- **Entities carry scalars, explicit id-reference relations, and ONE bounded read: a listing by a PREFIX of the declared id.** The port in `sqlite-in-the-browser` produced state equal to the original processor, so the model works; but two of its contortions came from the same hole, which is that `MutationContext` has no way to ask about a SET of rows. An ordered bounded array needed three entities plus a hand-maintained CSV index, and appending to a child list needed a hand-maintained count. The fix is the read side, not declarative aggregation. The Graph's own schema language is the prior art: a one-to-many is `@derivedFrom`, a virtual field that is "never actually created during indexing", so children are their own entities keyed by their parent and the collection is DERIVED WHEN READ; their *Avoiding Large Arrays* post is exactly this advice. A prefix listing is one indexed range scan on all three backends the spike measured (a PK prefix scan in SQLite, an `IDBKeyRange.bound([epoch], [epoch, []])` cursor in IndexedDB, a sorted walk in memory) and costs NOTHING at write time.
- **That listing is bounded BY CONSTRUCTION, and the bound is the decision.** The handler seam takes a prefix of the declared id plus a REQUIRED limit. Never an arbitrary `where` clause, never a caller-supplied `orderBy`: those are what make an accidental full scan possible, and a handler runs once per event on every backend including the ones with no query planner. The store's own richer query surface (`queryCurrent` / `queryAsOf`, which do take SQL predicates) is the SERVER-SIDE read layer and is unaffected; the point of the bound is that the HANDLER seam must be cheaply implementable by every backend, so it gets the one shape that is an indexed range scan everywhere.
- **Ordered children are keyed by something naturally unique, never by a dense array position.** A modelling rule, and the cheapest of the available fixes. The hand-maintained count in the port existed ONLY because the child's id ended in a dense array index: key the child by `(blockNumber, logIndex)` or an event ordinal instead and the append needs no count, the ordering IS the key, and the aggregation question never arises. This belongs in the authoring documentation next to the entity declaration, because it is the difference between an idiomatic model and three entities plus a CSV.
- **Materialised counts and declarative aggregation stay parked, and the measurement is now the reason rather than the shrug.** In a versioned store every child write opens a NEW VERSION of the parent, which on the real stream is **8,485 extra `placement` versions**, and version count is precisely the quantity that drove both footprint and per-write cost in the spike. Interfaces, timeseries, full-text search and grafting stay parked too. The trigger to revisit: a consumer needing an aggregate that a prefix listing plus a limit cannot serve cheaply. (Worth knowing when that day comes: the subgraph has no declarative count for this case either. Its `@aggregation` is interval rollups over timeseries, a different mechanism, and subgraph authors hand-maintain counters exactly as the port did.)
- **Retention is a declared capability, and its unit is BLOCK NUMBERS. One unit, one enforcement path.** A backend reports what it can serve (`revert-only`, a window of N blocks, or unbounded); the floor is the finality depth, because reorg revert already requires retaining superseded versions that far back; and pruning drops versions whose upper bound is older than the window. A window is a distance in block numbers compared against the tip's block number, and every backend prunes on that one comparison.
- **A window of N blocks is NOT N updates of history, and that misreading is the trap this spec walked into.** The measured stream is the launched stratagems game on Base, and its event-bearing blocks are median **429 blocks apart** (max 1,226,194). At a finality of 64, exactly ONE event-bearing block's history survives: the tip's. The naive reading, that a window of 64 gives 64 updates of history, is wrong by orders of magnitude on any real sparse contract, and it is wrong in the direction that produces confident wrong answers rather than errors. Read this bullet before changing a retention default.
- **The light backend advertises `revert-only`, and a read it cannot serve is a TYPED ERROR, never a tip read.** This REVERSES the earlier reasoning, which was "if backwards replay is fast enough within the finality window, advertise `asOf`". Replay speed was never the binding constraint. The mechanism is CORRECT wherever the patches still exist: on a dense stream, backwards replay matched the recorded state at every depth to 64, on Chromium, Firefox, WebKit and node, at a cost linear in depth (126 ms at depth 64 on a laptop). On the REAL stream there is simply nothing left to replay, because `History` prunes by block-number distance while the stream carries only event-bearing blocks. So the capability is withdrawn by SPARSITY, not by cost, and no amount of tuning returns it. The refusal is an error object of the same family as `NoSuchBlockError` (ADR-0015: an unresolvable block address is an error, not an empty result), so a caller discovers the missing capability at the call rather than from a plausible wrong number.
- **"Last N updates" is a RESOLVER at the edge, never a second retention mode.** The ergonomics are legitimate, the second enforcement path is not. Every backend already keeps a sparse index of the blocks that changed something, so "N updates" resolves to a floor BLOCK NUMBER with one indexed lookup and the existing block-number pruning does the rest. Adding it as a mode a backend must implement would duplicate the prune path, the capability report and the conformance tests for a unit that is derivable. If it is wanted, it is a helper above the seam.
- **Time is NOT a retention unit, at all.** On the READ side time is already solved: block addressing resolves a timestamp to the latest block at or before it, so "state around time T" needs no retention concept of its own. As a RETENTION unit it is actively wrong, because it would prune on WALL-CLOCK progress rather than on CHAIN progress: an indexer that stalls for a day would prune a day of history it never finished writing, and a chain that halts would have its whole retained window expire while the tip stands still. Retention keys on the thing that moves the tip.
- **The light path is a legitimate implementation of the seam, not a special case.** Immer reverse patches are a bounded history kept to exactly the finality depth, represented as a patch log rather than as versioned rows. The backends differ in representation, in as-of COST, and now in the retention they can honestly advertise on a sparse stream, not in the seam they sit behind. (Parked, with a trigger: immer's produced states share structure, so a light backend could KEEP the last K states instead of reconstructing them, measured at roughly 6 MB for a 64-state window and 52 MB for this game's entire history, turning an as-of read into an O(1) lookup. It does not survive a reload, so its honest capability is "as-of within the last K updates, in memory, reset on reload". Revisit when a consumer needs in-tab history that the block window cannot give.)
- **The pruning this spec promises does not exist yet, so it is a task and not a wiring job.** `@etherfold/state-store-sqlite` has NO pruning at all today, which means every backend it ships is effectively `unbounded` whatever a deployment sets, and the capability report would be a claim nothing enforces. The spike's footprint numbers were produced by pruning written inside the spike, not by the package.
- **IndexedDB is the browser default, under a stated condition rather than a preference.** Measured on the real workload it is not close: IndexedDB beats wasm SQLite on writes by 1.6x to 6.9x and on reads by 4x to 14x, on every engine that can run both. The condition for reversing it is all FOUR of: a Chromium-only target (Chromium's IndexedDB write path degrades roughly 10x as the store grows, and Firefox and WebKit do not degrade at all, so they have no crossover to reach), a live set past roughly 5,000 to 13,000 rows and still growing (this game peaked at 4,072), single-tab by construction or willing to build leader election (three of four tabs FAIL AT OPEN on both SQLite VFSs), and an app that can afford 501.9 KB gzipped plus a 130 to 190 ms cold start and does not need Safari (where OPFS is unavailable and SQLite silently becomes an in-memory database that loses everything on reload). **The ADR is owed by the task that actually wires the default**, not by this spec: the decision is worth an ADR (hard to reverse, surprising without context, a real trade-off), and it should be written where the condition and the overturning criteria sit next to the code they govern.
- **The seam placement is corroborated, not invented here.** `research/browser-embedded-indexer` re-scoped itself around exactly this question (raw `remote-sql` as the seam, forcing wasm SQLite into the browser, versus a higher seam letting the browser use a non-SQL store) and landed on the higher seam on evidence. This spec's `MutationContext` is that seam. Two independent routes to the same boundary is the strongest signal available that it is in the right place.
- **A captured, replayable stream fixture is the shared input. This LANDED while the spike ran** (`@etherfold/core`'s stream fixture: capture, `serializeStreamFixture` / `parseStreamFixture`, `replayStream`, plus the file form in `@etherfold/fs`), and it was built properly rather than as spike scaffolding for the reasons recorded here: deterministic replay is what makes processor tests reproducible, what lets two processor versions be compared on identical input, and what ADR-0008's blue-green rebuild reads from. The spike's browser harness fetched the fixture over HTTP and parsed it with the core's own parser, so the format is proven on all three engines. What remains is promoting the captured stream and the port into the conformance workload.
- **One conformance suite runs against every backend.** Versioned reads, as-of reads within the declared window, reorg revert including a counter that must decrease, and read-your-writes within a block. This is the mechanism that keeps two implementations honest, and it is worth more than either implementation.
- **Its workload is the stratagems port, promoted from the spike, and it EXISTS as committed artifacts.** Not an aspiration: `docs/spikes/sqlite-in-the-browser/fixtures/stratagems-alpha1.stream.json.gz` is the golden input (31,332 logs over 1,042 event-bearing blocks of the LAUNCHED game, `deployments/alpha1`, gzipped so it costs 0.6 MB in the tree instead of 20.5 MB), `fixtures/stratagems-alpha1.state.json` is the golden output computed by the ORIGINAL `JSProcessor`, and `src/port/` is the port that reproduced it byte-identically. Together they are a golden input, a golden output, and an equality oracle that is not our own reimplementation. A fixture is a SNAPSHOT by definition, so pinning it to a stratagems commit and block range keeps it honest indefinitely, which is exactly the property a vendored "real world example" would NOT have. Note the trap the spike hit: `contracts/deployments/base/` is the ABANDONED early deployment (45 logs), not the launched game; it is kept as the small smoke case and nothing else.
- **That fixture is not an example, and the distinction is load-bearing.** A teaching example must be readable in one sitting, which is why `GreetingsRegistry` (one event, one obvious question) stays the example in `examples/`. A conformance workload must be complex and real, which is why stratagems is unsuitable as a first example and ideal as a fixture. If stratagems is worth showing off, the honest form is a documented case study linking to the live repository, not a copy in `examples/` that silently stops matching it.
- **The query layer is generated from the entity declarations**, and the example ships hand-written routes rather than GraphQL. The GraphQL stack is already decided on measured evidence (Hono, then Yoga, then Pothos, built programmatically from the same model, no SDL and no deploy-time codegen; see `~/dev/github/wighawag/research/graphql-frontend-for-indexer-state`, researched 2026-06-02). Adding it later is an addition; failing to design entity declarations as the schema source now would make it a refactor.
- **The single-process CLI must not close the split seam.** `etherfold serve` runs fetching, processing and serving in one process, and that is the intended shape for the CLI case, but the log-fetcher / stream-builder / indexer-server boundary of ADR-0003 through ADR-0006 stays intact so a watcher and an indexer-server can be pulled apart without touching processors.

## Testing Decisions

- **The conformance suite is the centrepiece**: one suite, parameterised by backend, asserting external behaviour (what a read returns after a write, after a revert, as of a block) and never implementation shape. A new backend earns its place by passing it.
- **Reorg is the load-bearing case.** A stored counter that does not decrease when its block is reverted is the canonical bug this design is meant to make impossible, so it gets an explicit test on every backend rather than one shared happy-path test.
- **Capability claims are tested against behaviour**: a backend declaring an as-of window must answer within it and refuse outside it.
- Prior art to mirror: `packages/state-store-sqlite/test/`, and the reorg tests in `packages/processor-sqlite/test/reorg.test.ts` and `packages/js-processor/test/reorg.test.ts`.

## Out of Scope

- **Subgraph parity beyond the entity model**: interfaces, aggregations, timeseries, FTS5 and grafting. Parked with intent to revisit, per the decision above.
- **The GraphQL frontend itself.** Researched and decided elsewhere; this spec only guarantees the schema source it will consume.
- **A `remote-sql` adapter for browsers.** If the spike favours wasm SQLite, that adapter is a package in another repo (`remote-sql` currently ships libSQL, D1 and Durable Objects adapters and nothing for browsers), and it is that repo's work, not this one's.
- **Migrating existing processors.** Live consumers and published package names are explicitly not a constraint on this design.
- **Vendoring stratagems into `examples/`.** Its port graduates into the conformance workload instead, for the reasons recorded above.

The decisions above are kept rather than relocated because the ADR they will settle into (browser default equals IndexedDB, with its condition and its overturning criteria) is deliberately owed by the task that wires the default, not written ahead of it.

The browser story has a second, independent problem this spec does not solve but should not be confused with: state is persisted today by serialising the entire state blob to IndexedDB on every save (`keepStateOnIndexedDB`), which is O(total state) per write regardless of backend. Row-level writes make persistence proportional to what changed.

The spike baselined against that incumbent, and the honest result must be said before anyone promises a speed-up: **the whole-state blob is the FASTEST writer at today's sizes** (2.0 ms/block on Chromium, against IndexedDB rows at 45.6 and wasm SQLite at 74.2), so at 4,072 live rows row-level writes are a 20x throughput LOSS. What they buy is history, revert, bounded cold start, and a write cost that stops tracking TOTAL state: the blob's per-mutation cost climbs on a straight line with state size (11 us against an empty store, 26 at 2,700 live rows, 119 at 19,000), it cannot answer an as-of read, and it cannot revert. Sold as a speed-up, the first benchmark contradicts it; sold as correctness with a cost that stops growing, it is exactly what this spec is for.
