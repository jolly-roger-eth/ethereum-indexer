## What to build

One BigInt serialization codec, shared by every path that persists or serves a `LastSync`, that **identifies** a BigInt instead of **guessing** at one.

> **RE-SCOPED AGAIN 2026-08-25: the codec is now IN THE CORE, and one consumer is already migrated.** `ingest-wire-receiving-side` needed a BigInt codec for the wire, and adding a second tagged copy would have violated the very principle this task exists to enforce — so it did the extraction. `taggedBnReplacer` / `taggedBnReviver` now live in `packages/core/src/utils/bigint.ts` beside `bnReplacer` / `bnReviver`, and `@etherfold/processor-entities` (`src/cursor.ts`) imports them rather than keeping its own. **What remains is the migration, not the extraction**: `@etherfold/cli`, `@etherfold/browser`'s two keepers, `@etherfold/fs`, `@etherfold/core`'s own stream fixture and `@etherfold/conformance-workload-stratagems` are all still on the `"123n"` suffix. Core deliberately carries BOTH conventions right now, documented against each other; collapsing that back to one is this task's job. Read the two blocks below with that in mind — the "fix shape" section is now history rather than instruction.
>
> **READ FIRST — re-scoped 2026-08-24, because three of this task's premises drifted.** It was written 2026-08-21; since then `clear-the-release-path-and-archive-the-old-names` and `backend-neutral-entity-event-processor` landed. **(1)** The codec this task says to extract is no longer in `@etherfold/processor-sqlite/src/sync.ts` — it moved to `@etherfold/processor-entities/src/cursor.ts`, and `sync.ts` is now 37 lines of re-exports. **(2)** Two of the six named consumers, `ethereum-indexer-db-utils` and `ethereum-indexer-server`, are in `archive/`, which is outside the `pnpm-workspace.yaml` globs — so the PouchDB deep-walker and the HTTP wire-format decision are both out of scope now. **(3)** Two consumers exist that this task never named: `packages/core/src/stream/fixture.ts` and `packages/conformance-workload-stratagems/src/fixtures.ts`. The lists below are corrected; confirm them again before starting, since the drift-check in the prompt is what caught this.

The adapters that currently encode a BigInt by suffixing its decimal form with `n` and decode by recognising that suffix, **as they stand in the workspace today**: `@etherfold/cli` (`src/utils/bn.ts`, `src/keepState.ts`, the snapshot files), `@etherfold/browser`'s `keepStateOnIndexedDB` and `keepStateOnLocalStorage` (`src/storage/state/OnIndexedDB.ts`, `OnLocalStorage.ts`), `@etherfold/fs` (`src/utils/json.ts`, `src/utils/fs.ts`), `@etherfold/core`'s stream fixture (`src/stream/fixture.ts`), and `@etherfold/conformance-workload-stratagems` (`src/fixtures.ts`). The helpers themselves live in `@etherfold/core/src/utils/bigint.ts`. The convention is **irreducibly ambiguous**: `"123n"` is what a `123n` BigInt serializes to AND a perfectly legal string for a contract to emit, so the decoder cannot tell them apart. Guessing wrong silently rewrites event data, and it is silent in both directions: a real BigInt read back as a string breaks arithmetic downstream, a string read back as a BigInt breaks comparisons (including `===` against a hash) and JSON round-trips.

**The fix shape already exists, and it moved.** It is `@etherfold/processor-entities/src/cursor.ts`, which tags a BigInt as `{__bigint__: "123"}` — an object with a single reserved key that no decoded event value can collide with — and whose module note explains why a suffix convention has to guess. It got there via `backend-neutral-entity-event-processor`: the sync cursor moved behind the storage seam as an opaque string (ADR-0027), so the old `_sync (id, lastSync)` table became `_cursor (key, value)` in `@etherfold/state-store-sqlite` and the codec went with the processor rather than the storage. Extract THAT into the core next to `bnReplacer` / `bnReviver` / `isBigIntLiteral`, move every adapter above onto it, and have `processor-entities` use the shared one rather than its own copy. (`@etherfold/processor-entities` already depends on `@etherfold/core`, so this direction adds no cycle; the store packages must NOT gain a core dependency, which is what ADR-0018 and `no-platform-leakage.test.ts` pin.)

One thing to decide and record. **The read path**: whether the new decoder also accepts the legacy suffix form, and for how long. There are effectively no users and hash formats were already broken once (`535ccc1`), so "tagged only, no fallback" is defensible and simpler; accepting both means the ambiguity survives in the reader, which is the thing being removed.

**The server's HTTP wire format is NO LONGER part of this task**, and that is a scope reduction rather than an oversight. It applied to `ethereum-indexer-server`, which put `bnReplacer` output straight into response bodies and is now archived. The current `@etherfold/server` serves no BigInt-bearing payload (nothing in `packages/server/src` touches `bnReplacer`/`bnReviver`), and `ingest-wire-receiving-side` carries RAW logs — hex strings, decoded server-side — so the question does not arise there either. Re-open it as its own decision (with the ADR it was said to deserve) the first time an HTTP surface here serves a decoded `LogEvent`; do not settle an API shape in this task for a consumer that does not exist.

Prior art and the reason this exists: `535ccc1` made all six copies of the old decoder stop THROWING on values that were never numbers (they tested a string's first and last character, then called `BigInt()` on the middle, so an ordinary base36 hash such as `1x9tbhn` threw from inside `JSON.parse` and the CLI read a good snapshot as corrupt), and made `simple_hash` prefix its digests so they can no longer land on the ambiguous shape. Both were containment. The convention itself was left as a guess, deliberately, and this task is that residue.

## Acceptance criteria

- [ ] One codec in the core, used by the CLI, both browser adapters, the fs adapter, the core's own stream fixture, the stratagems conformance workload, and `@etherfold/processor-entities`. No package in the workspace keeps a private BigInt encoder or decoder. (`archive/` is out of the workspace and is not touched.) **The codec and the `processor-entities` half already landed with `ingest-wire-receiving-side`; the rest is what is left.**
- [ ] `bnReplacer` / `bnReviver` and `isBigIntLiteral` are GONE from the workspace, or their survival is an explicit recorded decision. Core currently holds two BigInt JSON conventions on purpose, which is a deliberate interim state and not the end state: leaving both is how the ambiguity survives in the reader, which is the thing being removed.
- [ ] A round-trip test per adapter proving a `LastSync` holding BOTH real BigInt event args and strings that merely look like BigInts (`"123n"`, `"0n"`, `"-5n"`) comes back with every value's original TYPE intact. This is the assertion the old convention cannot pass.
- [ ] A contract-emitted string that reads like a BigInt literal survives a round trip as a string, in the same document as a real BigInt. (Pin it with a decoded `LogEvent` whose args carry both.)
- [ ] The legacy-form decision is implemented and recorded: either legacy suffix input is rejected/ignored outright, or it is accepted with a stated end date and a test for each form.
- [ ] The sync cursor still round-trips on every backend after the move. `@etherfold/state-store` still declares NO dependencies and `no-platform-leakage.test.ts` still passes: the codec belongs to the processor, and the store persists a string it does not interpret (ADR-0027).
- [ ] The captured stream fixture still parses and replays byte-identically, and the stratagems workload still reproduces its golden state. These two are the reason the codec change is not free: they are committed artifacts, so a change of encoding is a change to files on disk, and whether they are regenerated or read with a compatibility path is part of the legacy-form decision above.
- [ ] Tests in each affected package's `test/`, vitest, and a changeset for every package whose serialization or API surface changed.

## Decisions

**1. The reader does not accept the legacy suffix form at all, and there is no fallback.** The ambiguity being removed lives in the reader, so a reader that still honours `"123n"` still has it. A `"123n"` string is now simply a string, everywhere. Alternatives considered: (a) accept both with an end date — rejected, it keeps the defect for the whole window and there are effectively no users; (b) translate on read — rejected, the translation *is* the guess; (c) refuse `/^-?\d+n$/` value-by-value — rejected outright, it would refuse legitimate event data, a worse failure than the one being fixed. Touches: every storage adapter, and anyone holding data written by a previous build.

**2. Where a persisted artifact carries a FORMAT number, the number was bumped and its reader refuses an unrecognised one; where it carries none, nothing was invented.** `STREAM_FIXTURE_FORMAT` 1 → 2 (`parseStreamFixture` throws, naming the file) and **the CLI's `SNAPSHOT_FORMAT` 1 → 2, which is a USER-VISIBLE behaviour change**: a snapshot at format 1 or in the bare pre-envelope form is now logged and treated as absent, i.e. a cold start, where it used to be read. That is the point — its BigInts cannot be recovered by this reader, so resuming would resume from state whose every `uint256` had become a string, and re-indexing is the CLI's existing recovery for a snapshot it cannot read. It removes the "still reads a legacy bare snapshot" behaviour that `cli/test/keepState.test.ts` pinned. The format-less artifacts (`keepStateOnFile`'s blob, `keepStateOnLocalStorage`'s, a bare published `lastSync` file) were deliberately NOT given an envelope: they are caches whose recovery is a re-index and whose `clear()` is one call, and adding persisted shape to reject data nobody holds is more machinery than the problem. Alternative considered: a `__FORMAT__` marker on all three keepers — rejected as new persisted surface for no live user; noted that the already-written-and-never-read `__VERSION__` is where such a check would naturally go (observation filed). Touches: `etherfold`'s resume behaviour, `@etherfold/fs`, `@etherfold/browser`.

**3. A KNOWN gap left open, written down at the call site rather than closed.** `keepStateOnIndexedDB` reads a remote snapshot published by the CLI's keeper, and that file *does* carry a format number — but the browser package does not read it, so a legacy published snapshot is installed rather than refused the way the CLI refuses the same bytes locally. Closing it requires `SNAPSHOT_FORMAT` to live where both packages can see it (`@etherfold/browser` does not depend on `etherfold`), which is a seam decision, not a line of code. Recorded in `OnIndexedDB.ts` and in ADR-0029's consequences. Touches: a future task, and anyone publishing snapshots.

**4. The two committed artifacts are REGENERATED, not read through a compatibility path**, and the migration's one unavoidable guess is *checked* rather than asserted. Reading a format-1 file necessarily makes the guess format 1 could not avoid; a fixture carries its own ABIs, so the migration refuses to write unless every value it converts is declared an integer. The proof that no meaning moved is separate and stronger than a diff: new golden → old rendering → byte-compare against `b40298e`. Alternative considered: a compatibility reader for format 1 — rejected, it is exactly the fallback decision 1 rules out.

**5. The stratagems `canonical()` renderer moved onto the tag too, which is a WRITE-side instance of the same defect.** Under `"123n"`, `123n` and the string `"123n"` render identically, so two states that genuinely differ compare equal and the oracle reports agreement it never established. Cost: 138 BigInts in a 24,067-line file, so the readability of the golden diff is essentially unaffected. Touches: the golden state files (regenerated) and `run/regenerate-golden-state.ts`.

**6. `simple_hash` keeps rendering BigInts as `"123n"`, and keeps its `h` prefix.** Those bytes exist to be hashed and are never parsed back, so there is no guess to make; changing either would change every digest ever persisted. The prefix is now belt-and-braces rather than load-bearing, and the `fp-` fingerprint prefix likewise. Documented in `hash.ts` and `fingerprint.ts`.

**7. Frozen spike scripts: re-pointed where they WRITE a shared artifact, left alone where they only measure.** `docs/spikes/sqlite-in-the-browser/run/verify-port.ts` writes the committed golden state, so leaving it on `bnReplacer` would silently un-migrate that file on the next run; it and its two siblings now use `taggedBnReplacer` (none of their committed result JSONs contains a legacy literal, so nothing on disk changed). `measure-snapshot-size.ts` keeps its local legacy replacer so its committed byte measurements stay reproducible; only its now-false comment was corrected, with the drift filed as an observation.

**8. Wrote `docs/adr/0029-one-bigint-convention-and-it-identifies-rather-than-guesses.md`.** It meets the gate: hard to reverse (format numbers bumped and consumed, committed artifacts re-encoded), surprising without context (a snapshot that used to resume now cold starts), and a real trade-off (ambiguity in the reader vs. a forced re-index). It also states explicitly what is still NOT decided: the HTTP wire format for a decoded `LogEvent`, which left this task with the archived server and gets its own ADR the first time such a surface exists.
