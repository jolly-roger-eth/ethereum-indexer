Changesets `.changeset/processor-version-cannot-lie.md` and `.changeset/bigint-literal-guard-and-hash-prefix.md`. 329 tests green across the workspace.
>
> **The task was built twice.** The first pass honoured backward compatibility: `getCodeFingerprint` was optional on `EventProcessor`, `configHash || 'not-configured'` was ruled out of scope, and both hash FORMATS were pinned by tests so that no existing deployment would be invalidated. The maintainer then confirmed there are effectively no users and a move to `@ethereum/indexer` with a version bump is coming, which makes invalidation free. Five decisions were reworked on that basis (2, 3, 4, 10 and 11 below), and the difference is not cosmetic: making `getCodeFingerprint` REQUIRED immediately surfaced three fake processors and two cache wrappers that silently lacked it.
>
> **Checking the task against reality first (as its prompt requires) held**, but building it surfaced a live bug the task never mentions, fixed separately in `535ccc1`: six copies of the same `"123n"` BigInt reviver decided a string was a BigInt from its first and last character, so an ordinary base36 `simple_hash` digest such as `1x9tbhn` threw from inside `JSON.parse` and the CLI read a perfectly good snapshot as corrupt, cold-starting permanently for ~1.25% of config hashes. A sweep test then showed a guard alone cannot fix it (`8918n` genuinely IS the convention's shape), so `simple_hash` now prefixes every digest. That bug would have swallowed this task's own fingerprint. What `535ccc1` did not fix, because it cannot be fixed by a better guess, is carried forward as `work/tasks/backlog/tagged-bigint-codec-across-storage-adapters.md`.

> **Re-scoped 2026-08-21**, after `sql-backed-event-processor` landed. The task was written when the JS-object processor was the only `EventProcessor` implementation. There are now two, the second reproduced the same `unknown` fallback on the day it was written, and the "where is the fingerprint persisted" question the original prompt told the builder to re-check now has two different answers. The failure modes and the chosen design are unchanged; the surface they apply to is wider. What changed is marked inline.

## What to build

`getVersionHash()` is the only thing standing between a processor logic change and state computed by the *previous* logic being served forever. Today it is an **optional, author-declared string** with a fallback, in **both** implementations:

| implementation | `getVersionHash()` today |
| --- | --- |
| `JSObjectEventProcessor` (`ethereum-indexer-js-processor`) | `` `${version \|\| 'unknown'}-${configHash \|\| 'not-configured'}` `` |
| `VersionedStateEventProcessor` (`@ethereum-indexer/processor-sqlite`) | `` `${version \|\| 'unknown'}-${simple_hash(entities)}-${configHash \|\| 'not-configured'}` `` |

Two failure modes follow, both silent, and both present in both:

1. **The author never sets `version`.** The hash is then a constant containing `unknown`, so no logic change ever invalidates anything.
2. **The author changes handler code and forgets to bump `version`.** Same outcome.

Today the consequence is a stale snapshot being reused. Under `docs/adr/0008` it gets worse: a version change is what triggers the blue-green rebuild, so a missed bump means **the rebuild never runs** and the server keeps serving state derived from logic that no longer exists, with no cold start to rescue it.

**The SQL path is partially, accidentally protected and that is not a substitute.** It folds the entity declarations into the hash, so a *schema* change invalidates without a version bump. Handler changes — the actual subject of this task — do not, because handlers are functions and the declarations are data. Treat it as a precedent for deriving part of the identity rather than declaring it, not as the problem being half-solved.

Build two layers, **across both implementations**:

- **Make `version` mandatory.** Required in the `JSProcessor` **and `SQLProcessor`** types, and a runtime throw at construction if it is missing or empty, so the `unknown` constant becomes unreachable rather than merely discouraged. This is a breaking change to two authoring surfaces and needs a changeset covering both packages.
- **Detect drift between the declared version and the actual code.** Derive a fingerprint from the processor's own handler implementations (the `on<Event>` functions, and `construct` / `handleUnparsedEvent` where the implementation has them), persist it alongside the existing context, and compare on load. If the **declared version matches but the fingerprint differs**, that is exactly the "forgot to bump" case: report it loudly.

The fingerprint is **advisory, not part of the version hash**. Including it in `getVersionHash()` would be safer in principle but would force a full rebuild whenever a bundler or minifier changes its output without any logic changing, which is an unacceptable cost on every deploy. Keeping it separate makes the false positive a warning rather than a multi-hour replay.

> **Know that this deviates from ADR-0008, deliberately.** That ADR says deriving the hash from the processor bundle itself "is a requirement of this design and not a follow-up" — i.e. it asks for exactly the folding-in that the paragraph above rejects. The rejection is on cost, and it is the reason this task exists in this shape rather than as "derive the hash from the bundle". Do not silently resolve the tension either way: build it advisory as specified, and record the deviation in your `## Decisions` block so a reviewer can ratify it or send it back. If it is ratified, ADR-0008's consequence bullet should be amended to match.

Default behaviour on drift is a loud error-level report that does not halt (the false-positive case is real: re-minification changes function source without changing behaviour), with an opt-in strict mode that refuses to start. Fail-loud by default, fail-stop by choice.

### Where the fingerprint is persisted (the drifted premise)

The original task said "persist it alongside the existing context in `lastSync`". That is still the right home, but it is no longer one place, and `ContextIdentifier` is a **core** type (`{source, config, processor}` in `packages/ethereum-indexer/src/types.ts`), so widening it touches the core and both implementations at once:

- **JS path:** `lastSync` is persisted only if a `KeepState` keeper is configured. A processor with no keeper has nowhere to write a fingerprint, so drift detection is a no-op there — decide whether that is acceptable (it is the in-browser case, which does usually have a keeper) or whether the absence should itself be reported.
- **SQL path:** `lastSync` is always persisted, as one row in the `_sync` table owned by `@ethereum-indexer/processor-sqlite`, serialized with a BigInt-tagged JSON codec. A new field rides along for free, but note the codec: a fingerprint must survive that round-trip unchanged.

Decide whether the fingerprint belongs **in** `ContextIdentifier` (one core change, both paths inherit it, and every existing persisted cursor lacks the field so absence must mean "unknown, do not report" rather than "drifted") or **beside** it in each implementation's own storage. Record the choice.

## Prompt

> Make a processor's version hash incapable of silently lying about its logic, in the `ethereum-indexer` monorepo.
>
> FIRST, check this task against current reality. It was re-scoped on 2026-08-21 after `sql-backed-event-processor` landed, so the drift that re-scope fixed is already reflected here; verify it is still accurate rather than assuming. Re-read `docs/adr/0008` (the blue-green rebuild premise, which held at re-scope time) and read `work/tasks/done/sql-backed-event-processor.md`, whose `## Decisions` block records why the SQL processor hashes its entity declarations and how its `_sync` cursor is stored. If something landed differently again, route to needs-attention rather than building on the stale premise.
>
> Context. `EventProcessor.getVersionHash()` is the processor-identity third of `ContextIdentifier` (`{source, config, processor}`); the core `load()` discards persisted state when it changes. There are TWO implementations: `JSObjectEventProcessor` via `fromJSProcessor` (the production path used by stratagems-world) and `VersionedStateEventProcessor` in `@ethereum-indexer/processor-sqlite`. Both build that hash from an OPTIONAL author-declared `version` string with an `unknown` fallback, so a processor with no version, or one whose author forgot to bump it after editing a handler, is indistinguishable from an unchanged one. The SQL one additionally hashes its entity declarations, which catches schema changes but NOT handler changes, so it is a precedent for deriving identity rather than a partial fix. `docs/reviews/server-cli-batch.md` (HIGH-2, MEDIUM-3) already flags the underlying problem; `docs/adr/0008` is what makes it load-bearing, because a version change is the trigger for the state rebuild.
>
> Do two things, in BOTH implementations. (1) Make `version` mandatory: required in the `JSProcessor` and `SQLProcessor` types and enforced at construction, and delete the `unknown` fallback so it cannot be reached. (2) Add drift detection: fingerprint the processor's own handler implementations, persist it with the sync context, and on load compare. Declared version equal but fingerprint different is the "forgot to bump" case: report loudly at error level by default, and refuse to start under an opt-in strict mode. Do NOT fold the fingerprint into `getVersionHash()` itself: a bundler or minifier change would then force a full state rebuild with no logic change, which is why it stays advisory. Note that this DEVIATES from ADR-0008, which asks for exactly that folding-in and calls it a requirement; build it advisory as specified and record the deviation in your `## Decisions` block rather than resolving the tension silently.
>
> Decide where the fingerprint lives, and record it: inside `ContextIdentifier` (a core type change both paths inherit) or beside it in each implementation's own storage. Mind that the two paths persist differently — the JS path only when a `KeepState` keeper is configured, the SQL path always, through the BigInt-tagged codec in `packages/processor-sqlite/src/sync.ts`.
>
> Watch two stability requirements. The fingerprint must be identical across process restarts for identical code, or it produces a drift report on every boot; test that explicitly, not just within a single process. And a cursor persisted BEFORE this change has no fingerprint at all: absence must read as "unknown", never as drift, or every existing deployment reports drift once on upgrade and the report stops being believed.
>
> Test at the `fromJSProcessor` seam in `packages/ethereum-indexer-js-processor/test/` and at the equivalent seam in `packages/processor-sqlite/test/` (vitest, mirroring `reorg.test.ts`'s style in each). Add a changeset covering every package whose authoring surface changed. Record any non-obvious in-scope decision durably per the work contract, and do not commit without confirmation.

## Decisions

Non-obvious choices the task did not specify, transcribed from the builder's final reports. Items 2, 3, 4, 10 and 11 are the amended second-pass versions: the first pass decided them under a backward-compatibility constraint the maintainer then lifted, and recording the superseded forms as if they described the code would be a lie in the record's own shape.

1. **The fingerprint lives INSIDE `ContextIdentifier` as `processorFingerprint`, and the CORE does the comparing.** Placement is forced, not preferred: `lastSync` is the one thing every persistence path round-trips WHOLE, and the CLI's `createFileKeepState.fetch` returns an explicit whitelist (`{state, lastSync, history}`), so a fingerprint stored *beside* `lastSync` would be silently dropped by the production snapshot path. The comparison is core-side because drift is defined relative to the core's own adopt-or-discard branch ("version hash equal, code different"), and the SQL processor deliberately returns its cursor even on a context mismatch, so an implementation-side check would have to re-derive that branch in two places. It is checked in the adopt branch BEFORE the state is adopted, so strict mode refuses without ever handing stale state to a listener. `indexerMatches` does not read the field, so a fingerprint can never cause a discard.

2. **`getCodeFingerprint(): string | undefined` is REQUIRED on `EventProcessor`, not optional.** An optional method is a hole with a polite name: an implementation that never wrote one, or a WRAPPER that forgot to forward it, would take drift detection down silently. Required makes both a compile error. This is what surfaced three fake processors (`feed`, `fetchLogs`, `updateProcessor`) and the browser fakes that lacked it, and both cache wrappers (`EventCache`, `ProcessorFilesystemCache`) now forward rather than answering for themselves, since a wrapper's own methods are identical for every processor it wraps and would hash to a constant. The RETURN stays nullable because "cannot tell" is a real answer, and the core reads it as "do not report" rather than "unchanged". `ProcessorContext.version` is required for the same reason.

3. **Both fallback constants are deleted, so every version hash changes and stored state is discarded once.** `${version || 'unknown'}` has nothing left to fall back to, and `configHash || 'not-configured'` is gone as well: the config is hashed the same way whether or not `configure()` was called. That second half also removes an asymmetry the task did not mention, where an unconfigured processor and one configured with `undefined` produced different hashes and discarded each other's state on no behavioural difference at all. The first pass kept both formats byte-identical (pinned by tests) to avoid invalidating deployments; that constraint was lifted.

4. **`simple_hash` no longer drops falsy values, and prefixes every digest with `h`.** The falsy drop is this task's own failure one layer down: filtering with a bare `if (value)` made `{fee: 0}` hash identically to `{}`, so a config change to a falsy value could not invalidate the state computed under the old one. `undefined` is still dropped, matching `JSON.stringify`, so a value hashed before and after a round trip still agree. The `h` prefix answers a bug found by the sweep test, not a hypothetical: a digest of all digits ending in `n` (`8918n`) IS a `"123n"` BigInt literal to the storage adapters, so it came back from storage as a BigInt and `processorHash === context.processor` then compared a string to a BigInt and discarded good state. No reviver can distinguish those; only the digest can, by never having the shape. Landed in `535ccc1` with the reviver fix, ahead of the feature that depends on it.

5. **What is fingerprinted, and how it is normalised.** Every function-valued property of the author's object (own and prototype, `constructor` excluded), read through property DESCRIPTORS so a getter is never invoked (fingerprinting must not run author code), keyed by property name, SORTED, each normalised by collapsing whitespace runs to a single space. Sorting means reordering handlers is not drift. Keying by name is load-bearing and was found by mutation testing: a METHOD's `toString()` carries its own name but an ARROW property's does not, so without the name in the payload, rewiring an arrow handler to a different event would be invisible. Non-function properties are excluded because `version`, `entities` and config are already in the version hash, and hashing them here too would make a config change read as CODE drift.

6. **Comments are NOT stripped from the fingerprinted source, deliberately.** Measured against this repo's own toolchain (tsc 6.0.3, esbuild 0.28 as vitest uses it): the fingerprint survives process restarts, reformatting and handler reordering; it does not survive minification, a transpiler or target change (tsc keeps comments and indents with four spaces, esbuild strips them and indents with two), or a comment edit under a toolchain that keeps them. Stripping comments would need a lexer that gets regex-vs-division right, and a lexer that gets it wrong deletes real code from the payload, after which a change inside the deleted region reads as NO drift. Over-reporting is recoverable by bumping the version; under-reporting is the failure this exists to prevent.

7. **An all-native fingerprint answers `undefined` rather than a hash.** If every handler is `.bind()`-ed or proxied, `toString()` says `[native code]` for all of them and a hash would be a CONSTANT that no change can move: the same silent lie as `unknown`. Partial coverage still fingerprints the readable handlers.

8. **The stored fingerprint is never refreshed after a report.** It describes the code that computed the state, so the report repeats on every boot until the author bumps `version` (which discards the state). Refreshing would let a real drift go quiet after being seen once, which is the same defect as never reporting it, delayed.

9. **The report goes out through BOTH `named-logs` at error level AND an `onProcessorDrift` callback.** A callback nobody sets is silent; a log nobody can route is hard to alert on. Log unconditionally so it is never silent, callback so a host can route it to a pager or a CI failure, throw only under strict. A listener that throws cannot break loading.

10. **Strict mode is indexer config (`strictProcessorDrift`), not a processor field.** The precedent sits immediately above it in the same type: `skipGenesisCheck` is also a load-time safety gate belonging to the deployment rather than to the processor an author ships. A CI job wants strict; the same processor in a browser does not. Default stays report-and-continue per the task, because the false positive (a re-minification) is real and independent of how many users exist.

11. **The version assertion lives in the core (`assertProcessorVersion`) and both implementations call it**, so the two paths say the same thing about the same failure. The JS path asserts TWICE: in `fromJSProcessor`, where the author's handler names still exist and make the message useful, and in `JSObjectEventProcessor`'s constructor as a backstop for the exported class. `reset()` no longer re-reads `version` from the source object, since version is per-instance identity fixed at construction and a re-read could pick up a mutated empty string after the guard had passed.

12. **DEVIATION FROM ADR-0008, deliberate and NOT resolved by the builder.** ADR-0008 says deriving the hash from the processor bundle "is a requirement of this design and not a follow-up". This builds the fingerprint ADVISORY instead, per the task, because folding it into `getVersionHash()` would force a full state rebuild whenever a bundler or minifier re-emits the same behaviour differently. The builder left the ADR untouched and flagged the tension for a reviewer rather than resolving it either way.

    **Ratified 2026-08-21.** The maintainer accepted the deviation, and ADR-0008 now carries an `Amended` section that withdraws the bundle-derivation requirement and records what replaced it. The amendment states the residual risk that ratification accepts, which this record should not soften: a missed bump still does not trigger the rebuild, because the rebuild keys off the version hash and the fingerprint is deliberately not in it. What changed is that the condition is now announced on every load instead of being invisible, and `strictProcessorDrift` is the fail-stop for a deployment that cannot tolerate it.

## Follow-on

- **The ADR-0008 tension is closed, in the ADR.** Ratified and amended on 2026-08-21; see decision 12. The ADR, not this record, is where the current position lives, including the risk the ratification accepts.
- **The `"123n"` BigInt convention is still a guess in five adapters, plus the server's HTTP bodies.** `535ccc1` made every copy stop THROWING on values that were never numbers, and stopped `simple_hash` producing the ambiguous shape, but the convention still cannot distinguish a real BigInt from a contract-emitted string that reads like one. Carried forward as `work/tasks/backlog/tagged-bigint-codec-across-storage-adapters.md`, which holds the mechanism and the fix shape (`processor-sqlite`'s tagged `{__bigint__: "..."}` codec); the observation note that first recorded it was discharged on capture, per the work contract.
- **`updateProcessor` has its own forgot-to-bump path, untouched here.** `indexer.ts` warns when a swapped-in processor has the same version hash and skips the swap. It now has a fingerprint available to say something much sharper than "if this is unexpected, bump the version hash", and does not use it.
- **The fingerprint is advisory, so nothing acts on it.** Under ADR-0008's blue-green rebuild, a drift report is precisely the signal that a rebuild SHOULD have been triggered and was not. Wiring it to anything (a refusal in CI, a rebuild trigger, a status field on the server's `/` route) is deliberately out of scope and unbuilt.
