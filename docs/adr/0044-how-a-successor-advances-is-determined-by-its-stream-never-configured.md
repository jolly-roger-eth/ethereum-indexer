# How a successor GENERATION advances is DETERMINED by its stream, and is never configured

A **generation** is a stream plus a fold over it, and an **indexer** holds several. When a second generation is built beside the live one, something has to decide how it catches up. We decided that **the decision is DETERMINED by whether it shares a stream with a generation already held, and that there is no configuration knob anywhere that can override it**: a generation on a SHARED stream is a **follower** that fetches nothing at all and re-folds the stored stream then follows it, and a generation on its own stream is an ordinary indexer at a different address. Because read and write share ONE `ExistingStream` seam, "a generation that merely reads" is not expressible by declining to write — so a follower is handed a **read-only stream view** (`readOnlyStream`) whose `saveNewEvents` and `clear` are no-ops, which is what makes the **one-writer rule** structural rather than conventional.

## Considered Options

- **A knob on the successor** (`{advance: 'follow' | 'fetch'}`), which an earlier draft of `a-reconfigure-is-not-an-outage` offered. **Rejected, and it is the reason this ADR exists**: both positions of the knob are wrong in one of the two cases. "Follow a stream nobody writes" never advances at all; "fetch a stream somebody else writes" makes a second writer, silently, on a seam where the save is driven by the indexing loop rather than by the caller's intent. A knob whose only correct value is derivable from the data is not a choice, it is a way to be wrong.
- **Give the follower a head-following poller**, so it fetches only the tail rather than the history. This is the option that looks cheap and is not, and it breaks three things at once. The spec's own test says a processor-only change re-fetches NOTHING — "zero, not fewer" — and a poller makes it fewer. The one-writer rule goes, because `promiseToSave` calls `saveNewEvents` unconditionally. And, decisively, the successor's state becomes a function of ITS OWN FETCH rather than of the stream, so re-folding the stored stream later yields a DIFFERENT state: a generation stops being "a stream plus a fold over it", and the promise that moving the **canonical pointer** back restores answers EXACTLY (story 4) dies with it, taking ADR-0008's rebuild-from-the-stored-stream story along.
- **Express read-only by simply not calling `saveNewEvents`.** Rejected because there is nowhere to not call it from: the engine's save is unconditional and belongs to the indexing loop. The seam is where the distinction has to live.
- **A second, parallel read-only implementation of the seam.** Rejected: `replayStream` (a captured fixture) was already exactly this shape, so `readOnlyStream` generalises it and `replayStream` is built out of it. Two definitions of "read-only on this seam" would drift, and the one that drifted would be the one nobody was watching.

## Consequences

- **Which generation WRITES a stream is the FIRST one held on it** — registration order, not the canonical pointer. Promotion is one small record write and must not silently hand the append duty to a different engine mid-flight; in the ordinary case the two coincide anyway, since the registry makes the first generation registered canonical.
- **A follower is at most one cycle behind at the tip**, because `Indexer.indexMore` steps generations in the order they were built and a stream's writer is always ahead of anything following it. That is a latency cost, accepted deliberately in exchange for the exact re-fold; it is not a correctness cost, because the next tick closes it.
- **A follower cannot advance past what the writer has written.** If the writer stops, so does the follower. That is the correct dependency — a follower's whole claim is that its state is a function of the stream — but it means deleting or pausing a stream's writer strands its followers, which the pause and promotion landables have to account for.
- **A follower never CLEARS.** The load path clears the cached stream on every shape it cannot use, and a follower takes those branches over a stream another generation is still indexing into, so `readOnlyStream.clear` is a no-op for a sharper reason than symmetry: passing it through would delete the live generation's history. A follower that cannot read the stream returns and asks again next tick.
- **Two generations under one container share one stream CONFIG.** A different FILTER is nameable per generation (`GenerationSpec.source`) and is what the separate-stream case needs; a different stream CONFIG is not, because `setStreamConfig` is a single mutable value on the ONE keeper a container holds. A config-differing generation needs a keeper per generation, and nothing needs it yet.
