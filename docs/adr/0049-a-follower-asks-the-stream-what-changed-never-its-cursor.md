# A follower asks the STREAM what changed, never its cursor

A **follower** (a generation on a shared stream, ADR-0044) advances by re-reading the stored stream from where it resumes and replaying whatever is beyond its own fold, so it needs a cheap way to decide there is nothing to do — otherwise every idle cycle re-decodes and re-walks the window. That test used to be a comparison of the stream's stored CURSOR against its own (`lastSyncStored.lastToBlock <= current.lastToBlock`). We decided that **the question "has this stream changed" is asked of the STREAM'S CONTENT and not of any cursor**: a follower remembers the emissions it last folded over the range it resumes from (block hash, index in the block, and whether it was an application or a retraction — the identity `sameEvent` already uses) and does nothing only while what the stream holds there is emission-for-emission the same list. The stored cursor still contributes the half it cannot be wrong about: a stream reaching PAST this fold is new by definition.

The cursor version was not merely imprecise, it was silently WRONG once ADR-0045 landed. A paused writer caps `toBlock` at the cursor it paused on, so a reorg it detects at or below that cap during its drain is appended to the stream — retraction and replacement both — while `lastToBlock` never moves. A follower level with the cap concluded there was nothing to follow and went on answering from a branch the chain had abandoned, with nothing reporting it. Neither rule was wrong on its own: the guard was written when a frozen cursor could not exist (a running writer's `lastToBlock` rises with the tip every cycle) and pause created one. The defect lived only where they met, which is why the fix is not on either side but in what the follow path ASKS.

## Considered Options

- **Keep a cursor comparison and add the missing dimension** (compare `latestBlock`, or the stored `lastFromBlock`, or the pair). Rejected: those move for reasons that have nothing to do with an append — a paused writer's `latestBlock` tracks the real head every block — so a follower would re-walk the window on every cycle of a stream nobody is appending to, which trades a correctness bug for a performance one. And it repeats the original mistake in a new place: every one of them is a SUMMARY the writer maintains, and the next thing that freezes or repurposes one puts this bug back.
- **Delete the early return and replay unconditionally.** Correct — a replay of what is already folded de-duplicates against the unconfirmed window and delivers nothing — and rejected on cost: it re-decodes (`reparse`) and re-walks the window on every cycle of every follower forever, including the overwhelmingly common case where nothing has happened.
- **Have the writer publish an append COUNTER or a stream digest for followers to poll.** Rejected as the same class of thing one level up: it is another summary that can disagree with the stream, it needs a new field on a cursor contract ADR-0035 deliberately keeps to four properties, and it would have to be maintained by every keeper implementation. The follower already has the events in its hand — `fetchFrom` returned them — so there is nothing to publish.
- **Make a paused writer move its `lastToBlock` when it appends.** Rejected outright: the frozen cap IS the drain's termination condition (ADR-0045), so moving it would stop a pause ever reaching `drained`.

## Consequences

- **The memory is bounded by the finality window, not by the stream.** A follower level with the stream resumes at `latestBlock - finality`, so the list it holds is the emissions in the reorg window; a follower that is BEHIND holds more, but it is folding rather than idling, and the list is replaced each time it folds. Nothing is persisted — a reload re-folds the stored stream from the start, which is the follower's normal first advance.
- **It cannot go stale the way `lastToBlock` did, because it is not a claim ABOUT the stream — it is the stream.** The comparison is against the exact bytes the next replay would consume, so any append into that range (a retraction, its replacement, a block no cursor mentions) makes the two lists differ whatever any cursor says. Its failure direction is also the safe one: it is set ONLY where this generation has just folded that exact slice, so "unknown" means FOLD, and an unnecessary replay costs a walk and delivers nothing.
- **The shortcut fires slightly less often than the cursor comparison did**, by design: when the follower's resume point moves, the slice loses its lowest emissions and the lists differ, so it replays once more before settling. That is one de-duplicated walk after an advance, not a per-cycle cost.
- **A cursor-derived shortcut is now the thing to be suspicious of on this path.** Anything that summarises a stream into a number can be frozen, capped or reused by a mechanism that does not know a follower is reading it. If a future optimisation wants one, it owes an answer to "what freezes this, and what happens to a follower level with it".
