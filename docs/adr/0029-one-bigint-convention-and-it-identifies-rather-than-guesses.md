# There is ONE BigInt convention, it TAGS rather than suffixes, and a persisted artifact refuses the old one by its format number

Every path in this repo that puts a `LastSync`, a decoded `LogEvent` or a wire batch into text encodes a BigInt as `{"__bigint__": "123"}` and decodes it from that shape and no other (`taggedBnReplacer` / `taggedBnReviver`, `@etherfold/core`). The `"123n"` suffix convention that the CLI, both browser keepers, the fs adapter and the captured stream fixture used is **removed rather than deprecated**, and there is no fallback in any reader.

The suffix convention is irreducibly ambiguous, and that is a fact about the DATA rather than about any implementation of it: `"123n"` is what `123n` serializes to AND a perfectly legal string for a contract to emit, so a decoder has to guess, and guessing is silent in both directions. A real BigInt read back as a string breaks arithmetic downstream; a string read back as a BigInt breaks comparisons (including `===` against a hash) and JSON round-trips. Both kinds genuinely coexist in one document: `LastSync.unconfirmedBlocks` carries decoded events whose `args` hold a BigInt per `uint256`, and the same document carries `context` digests. Two earlier fixes (`535ccc1`) stopped the decoder THROWING on values that were never numbers and gave `simple_hash` a leading `h` so its digests could not land on the shape; both were containment, and neither could reach the guess.

## The read path: no fallback, and a format number where one exists

Accepting both forms was the alternative, and it is the one that fails on its own terms: the ambiguity being removed lives in the READER, so a reader that still honours `"123n"` still has it. So a `"123n"` string is now simply a string, everywhere.

That leaves the question of data ALREADY on disk, and the answer is deliberately split by whether the artifact can say what it is:

- **It carries a format number.** Bump it, and let the reader refuse the file as a whole. `STREAM_FIXTURE_FORMAT` and the CLI's `SNAPSHOT_FORMAT` both went to 2. This is the important half: a refusal is loud, and it is strictly better than the alternative available here, which is handing back a document whose every `uint256` has quietly become a string. For the CLI that means a snapshot written by an older build is logged and treated as absent, which cold starts — the same recovery an unreadable snapshot already had.
- **It carries no format number** (`keepStateOnFile`'s blob, `keepStateOnLocalStorage`'s, a bare published `lastSync` file). Leave it. These are caches whose recovery is a re-index and whose `clear()` is one call, and giving each an envelope to reject a state nobody holds would be more machinery, and more persisted shape, than the problem. Their legacy content reads back as the strings it now is.

Refusing `"123n"` value-by-value was considered and rejected outright: it would refuse legitimate event data, which is a worse failure than the one being fixed. Translating it on read was rejected for the same reason accepting it was — the translation IS the guess.

One gap in that rule is left open KNOWINGLY. `keepStateOnIndexedDB` reads a REMOTE snapshot published by the CLI's keeper, and that file does carry a format number — but the browser package does not read it, so a legacy published snapshot is installed rather than refused, the way the CLI refuses the same bytes locally. Closing it means `SNAPSHOT_FORMAT` has to live where both packages can see it (today it is the CLI's own constant, and `@etherfold/browser` does not depend on `etherfold`), which is a seam decision rather than a line of code. It is written down at the call site so it is a known gap and not a silent one.



## Why the tag is an object with one reserved key

A single-key object cannot be produced by a decoded log value: `args` keys come from the ABI, and a fixed sentinel string prefix (`"bigint:123"`) or a type-prefixed string would put the convention right back in the string space where a contract can imitate it. The reviver additionally refuses an object that merely CONTAINS the key alongside others, so the shape is exact rather than a prefix match.

## Consequences

- **Committed artifacts in the old encoding were re-encoded once, not read through a compatibility path.** The two stratagems stream fixtures and their two golden states are files on disk in the format being replaced. `docs/spikes/tagged-bigint-codec-across-storage-adapters/` holds the migration and, more importantly, the proof: the migrated stream, replayed and re-rendered in the OLD encoding, is byte-identical to the golden as committed at `b40298e`, so the state behind the rendering did not move. The migration inherits format 1's guess exactly ONCE, and for these files it is decidable rather than assumed — a fixture carries its own ABIs, and the migration refuses to convert any value whose declared type is not an integer.
- **The one surviving `"123n"` is inside `simple_hash`**, which renders a BigInt that way purely to have bytes to hash. Nothing decodes those bytes, so there is no guess to make; and the digest keeps its `h` prefix even though what it guarded against is gone, because dropping it would change every digest ever persisted.
- **`bnReplacer`, `bnReviver` and `isBigIntLiteral` are gone from `@etherfold/core`**, and `bnReviver` from `@etherfold/browser`. There is nothing left in the workspace to reach for by mistake.
- **`@etherfold/state-store` is untouched and still declares no dependencies.** The cursor is an opaque string at the seam (ADR-0027) and the codec belongs to the processor, so this change stops at that line, as `no-platform-leakage.test.ts` pins. `state-store`'s `describeValue` renders a BigInt as `123n` in an ERROR MESSAGE, which is JavaScript's own literal syntax for a human to read and not a codec.
- **The HTTP wire format for a decoded `LogEvent` is settled for the INGEST direction and undecided for a served one.** `@etherfold/server`'s `POST /ingest` already carries decoded `LogEvent`s — `WireBatch.logs` is `LogEvent<ABI>[]`, and `ingest-wire-receiving-side` recorded that it reads ADR-0004's "raw logs" as _raw as opposed to reorg-annotated_ rather than _undecoded_ — and it encodes them with `serializeWireBatch` / `parseWireBatch`, i.e. this codec. So a sender (`agnostic-log-fetcher`) has its answer today and must not invent another. What is NOT decided is a surface that SERVES decoded events in a response body: the one server that put suffixed BigInts into response bodies is in `archive/`, and versioning and content negotiation for a public read API deserve their own ADR when such a surface exists rather than a default set here.
