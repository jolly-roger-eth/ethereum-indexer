# A generation is built STATE FIRST, and its factories are supplied PER GENERATION

A **generation** is identified by its **stream** plus its processor's version hash, and an **indexer** (`Indexer`, `@etherfold/core`) holds several of them, each folding into its OWN state. So the container cannot be handed one already-constructed processor over one already-constructed store: it has to BUILD a generation. The obvious way to express that is a state factory keyed on the generation's identity — `createState(generationId)` — and it cannot work, because the identity is not knowable at that point: the stream half comes from the source and the stream config, but the FOLD half is `processor.getVersionHash()`, the processor needs its state, and the state was supposed to be keyed on the identity. It deadlocks worse on a RELOAD, where finding the generation's record requires the version hash, which requires the processor, which requires the store the record was supposed to name.

We decided that **a generation arrives as a `GenerationSpec` of two factories called in one order — `createState` then `createProcessor(state)` — and that the spec is supplied PER GENERATION rather than once for the container**. The container computes the stream digest (which it can), hands it to both factories as context, and REGISTERS the generation afterwards from the processor's own version hash. Nothing declares an identity twice, so nothing can declare it wrongly, and what distinguishes this generation's state from the next one's is the caller's own closure: a reconfigure supplies a new spec, and that spec names the store its fold writes to.

## Considered options

- **`createState(generationId)`, one state factory for the container.** The shape everyone reaches for first. Rejected because of the circularity above; it is only writable by pretending the fold's identity is known before the fold exists.
- **Have the caller DECLARE the version hash beside the factory**, so the identity is complete up front. Rejected: on the only authoring path that exists, the value is `${version}-${simple_hash({entities, config})}` (`EntityEventProcessor`), so an app cannot type it and would have to duplicate a formula it does not own. A declaration that can silently disagree with `getVersionHash()` would key a store on a lie, and checking it turns into a refusal for a value nobody could have supplied correctly.
- **Build the processor over a probe/no-op store to read its version, then build the real one.** Rejected: it opens a store nobody wanted (a real IndexedDB database, on the runtime where storage is argued at length), and it rests on the unwritten rule that a processor touches nothing in its constructor, which nothing enforces.
- **Give the state factory a lazy store handle resolved after registration.** Rejected: every read on the seam is async but `capabilities` is not, so the indirection cannot be honest, and it makes the construction order depend on a Proxy nobody would expect to be there.

## Consequences

- **The container never verifies an identity, it OBSERVES one.** `registry.create({stream, processor: processor.getVersionHash()})` is the only place a generation is named, and `create` RESOLVES an already-registered identity, so a boot that names its own generation on every start neither duplicates nor pushes against a cap.
- **A registered generation this container has no spec for cannot be run**, which is `CanonicalGenerationNotHeldError`: it is refused rather than silently promoting the generation that WAS built, because which generation answers reads is not a decision an open may take on its own. Resuming several generations across a restart is the promotion policy's and the shared-stream follower's business.
- **`createIndexerState` (`@etherfold/browser`) takes the same two factories**, which is what makes "the store is the deployment's choice" survive into a world with N generations: the same `fromEntityProcessor(processor)` is the processor factory, and `createBrowserStateStore(...)` is the state factory, one call each per generation.
