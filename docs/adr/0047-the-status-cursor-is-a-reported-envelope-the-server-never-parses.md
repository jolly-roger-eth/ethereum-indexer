# The `/status` cursor is an envelope around a value the server never parses, and the generation dimension grows inside it

`/status` reports how far the pipeline has got as `cursor: {reported: true, value: <whatever the host's reporter returned>}`, or `cursor: {reported: false, reason: <why not>}`, and the field is ABSENT on a host that injects no reporter. The value is placed in the response verbatim: `@etherfold/server` has no store dependency and the sync cursor is an opaque string behind the storage seam (ADR-0027), so only the process that owns the store can read one and only the processor knows what one means. The server owns the ENVELOPE; the host owns the CONTENTS.

Recorded because it is a PUBLISHED RESPONSE BODY. Once an operator's dashboard or a client reads `cursor.value`, the shape is expensive to change, and the obvious cheaper shapes (`cursor: "<string>"`, `cursor: 4242`) are exactly the ones the next piece of work would have to break.

## Considered options

- **A bare scalar** (`cursor: 4242`, or the opaque string itself). Rejected twice over. An indexer already holds several **generations** and reports progress per generation (`a-reconfigure-is-not-an-outage`); the server does not hold generations yet (`the-server-and-cli-hold-generations-too`), so it reports ONE cursor today — but a scalar could only grow that dimension by CHANGING ITS TYPE under readers. And the opaque string is a serialized `LastSync` carrying an unconfirmed window of decoded events, so reporting it raw would put an unbounded blob on the page an operator refreshes while something is wrong.
- **A parsed, server-defined shape** (`cursor: {lastToBlock, latestBlock}`). Rejected: it gives `@etherfold/server` a cursor's MEANING, which ADR-0027 deliberately keeps behind the seam, and it would freeze one processor's notion of progress into the HTTP contract of a package that must run against any processor.
- **Omitting the field on failure** rather than reporting a reason. Rejected: an operator looking at a status page cannot then tell "this deployment reports no cursor" (a Worker, a read-only `serve` tier) from "this deployment's reporter is broken", which is precisely the distinction the page exists to make.

## Consequences

- **The generation dimension grows INSIDE the field, additively.** A host that later reports several generations adds a key beside `value` (`cursor: {reported: true, value: <the canonical generation's report>, generations: {...}}`), so `value` keeps meaning "the generation answering reads" and no existing reader breaks. That is the growth path this shape was chosen for; adding a SECOND top-level field for generations, or re-typing `value` into a map, would forfeit it.
- **The server verifies that a report can be SENT, and nothing else.** `JSON.stringify` is called on the value inside the degrade path, because an unserialisable report (a `bigint`, which is what every decoded `uint256` in this project is) would otherwise throw inside `c.json` where nothing can catch it, and answer `500` on the health page. That is a serialisability probe, not parsing: it asks nothing about what the value means. The reporter's return type is JSON-shaped for the same reason, one layer earlier.
- **The size constraint lives in the option's doc comment and can only live there.** The server reports verbatim, so it cannot bound what it was handed; a host that hands over the raw serialized cursor breaks the page and no server-side check can save it.
- **A reporter cannot take `/status` down.** Throwing, rejecting, having nothing to report and being unserialisable all degrade to `{reported: false, reason}`; none of them changes `healthy` or the status code. Same rule the reorg counters already follow in that route: an operational read that could fail the health page would be worse than no operational read.
