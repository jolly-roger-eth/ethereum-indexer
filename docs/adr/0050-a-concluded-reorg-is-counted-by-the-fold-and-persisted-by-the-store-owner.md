# A concluded reorg is counted by the FOLD and persisted by whoever owns the store

The reorg counters on `/status` were written from one place, the HTTP ingest route (`recordReorgSafely` in `@etherfold/server`), which quietly made an operational counter a fact about the TRANSPORT. A COMBINED process folds through `createDirectIngestion` and touches no route, so `etherfold run` reverted state on a reorg correctly and then reported `{absence: 0, contradiction: 0}` for ever, while `etherfold index` folding the identical chain reported the revert it made -- and `build` had no `Meta` table at all. The gap sat on the deployment shape the milestone calls the default, and on the one number an operator watches to tell "my RPC provider is truncating results" from "the chain reorged" (ADR-0004).

We decided that **the count is taken where the reorg is CONCLUDED and written by whoever OWNS the store**. `StreamBuilder.receive` calls a `ReorgRecorder` exactly once per concluded revert, whichever entrance the batch arrived through; the deployment that opened the database supplies that recorder (`buildProcessor`, `etherfold`); and the ingest route is a CALLER of `receive` rather than the owner of a write. The DURABLE KEY NAMES live in `@etherfold/core` beside `ReorgCause`, because the writer and the reader are deliberately in different packages: a read tier (`etherfold serve`) owns no store, holds no processor and still has to answer "how many reverts does this database record" off a database it did not write.

## Considered options

- **Have the CLI call `@etherfold/server`'s `recordReorg` itself, from each folding command.** Rejected on two counts. It makes the CLI depend on the server package for a WRITE to a database the CLI itself opened, and it puts the same write at three call sites plus the route -- so the shape that both CONCLUDES and RECEIVES (a split receiver: its stream-builder derives the revert, its route serves the request) gets two, and double-counts. A structural single site is what makes "exactly once" a property rather than a discipline.
- **Leave `run` blind and document it.** Rejected. `run` is the default thing to reach for (`CONTEXT.md`, "The COMBINED deployment is the milestone"), and the absence-versus-contradiction RATIO is the whole diagnostic: a rising absence rate means truncation or misconfiguration, not chain activity. A deployment shape that cannot report it is missing the signal on the shape most people run.
- **Move the counters behind an injected reporter, the way the cursor is (ADR-0047).** Rejected, and it is the tempting symmetry. The cursor is opaque behind the storage seam and only its owner can read one; the counters are ROWS IN THE SERVER'S OWN `Meta` TABLE, and the process that must report them is frequently a read tier that owns no store at all. Injecting the READ would leave `serve` with nothing to report, which is the opposite of what this fixes.
- **Put the write in `@etherfold/state-store-sqlite`, the package that already owns a libSQL database.** Rejected: a store backend must not depend on `@etherfold/core` (ADR-0016, and the reason ADR-0027 keeps the sync cursor an opaque string), and it would need `ReorgCause` and the key names to do this.
- **Keep the keys in `@etherfold/server` and let the CLI import them.** Rejected for the same dependency reason as the first option, one level down. The keys went to core instead, which is the only package both ends already depend on and the one that decides what a `ReorgCause` IS.

## Consequences

- **`@etherfold/server` no longer exports `recordReorg`.** It reads (`readReorgCounters`) and writes nothing, and its dependency posture is unchanged: it still owns no store package. A host that embeds the server and wants counts supplies a recorder to the `StreamBuilder` it builds, exactly as it already supplies the database, the environment, the ingestion and the cursor reporter.
- **`etherfold build` applies the fixed-table schema, which it never did.** The one-shot binds no port, so nothing else ever would, and a database it emitted carried neither a schema version nor a reorg count. That is the failure being prevented: `build` exists to emit a publishable ARTIFACT later fed into another process, and a database that loses its provenance the moment it becomes an INPUT is worse than one that never had it. So the fixed tables are a property of the ARTIFACT rather than of whichever process happens to be serving it. `run` and `index` are unaffected -- they bind a port, and `--no-auto-setup` still declines the tables there.
- **A failing counter write can never take down a fold, on any shape.** The guarantee `recordReorgSafely` gave the route is owed by every shape now, so it lives in `StreamBuilder.noteReorg`: it runs AFTER the batch was applied, and it catches and logs. Losing a count is a far better trade than rolling back the state it describes, or than a `500` telling a sender to re-send a batch that was in fact applied.
- **`IngestionOutcome.reorg` is REPORTED and never delegated.** It stays on the outcome (a caller logs it, answers a sender with it, or decides what to do next), but nothing counts from it. A caller that did would count only on the shape it happens to be, and twice on the shape that is both. `packages/core/test/oneReorgWriteSite.test.ts` scans the workspace and asserts one write site.
- **The reorg log line moved into core with the count.** A combined process has no route to log a revert from, and the absence-driven one is the line an operator must see.
