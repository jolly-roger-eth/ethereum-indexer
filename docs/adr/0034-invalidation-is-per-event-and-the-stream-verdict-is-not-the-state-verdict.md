# Invalidation is computed per event, and the stream verdict is not the state verdict

`ContextIdentifier.source` carries one entry per (contract, event, live range) whether or not the source declares ranges, over a leading SKELETON entry at block 0 for what an ABI cannot describe (`chainId`, `genesisHash`, each contract's `address` and `startBlock`); a non-event ABI member contributes to nothing. Each entry carries TWO digests, and `sourceInvalidationOf` returns TWO verdicts computed from them: a STREAM half over `streamHash` (the address, the `topic0` and the range: what the fetch filter is built from) and a STATE half over `hash` (the address, the canonical signature, the DECODING SHAPE and the range: what a fold over decoded events rests on). Both halves keep `invalidFromBlock`.

The reason is that an ABI is REGENERATED and not hand-edited, so the things that move in it most often are the things nothing depends on. Adding a view function, reordering the array, or recompiling into a different `internalType` used to discard the state AND re-fetch every block ever indexed. And the fetch and the fold do not depend on the same thing: `topic0` hashes types and not names, so a renamed non-indexed parameter leaves every cached log exactly right and every cached `args` filed under a key the handler no longer reads.

## Considered options

**One verdict, as before.** Rejected because it cannot express the case that motivates the whole change. A renamed parameter has to keep the stream and discard the state, and a shrunken topic set leaves a strict SUPERSET which is reusable by decoding less. One verdict forces the conservative answer on both, which is a complete re-fetch for a change no log can see.

**Comparing entries ELEMENT-WISE BY INDEX**, which is what the ranged path did, was abandoned. It was workable while every entry was per-RANGE and the list was ordered by `startBlock`, so an append landed at the end. It is not workable now that an un-ranged source puts every one of its events at the same block: inserting an event shifts whatever sorts after it, and every shifted entry would read as a change to something already indexed. The comparison is a SET DIFF on digests instead, which asks the question that was always meant (which entries are NEW, which are GONE) and is immune to where they land. As a side effect an entry EDITED above the cursor now costs nothing, where by-index it invalidated: nothing above the cursor was ever indexed, so there is nothing derived from it to be stale.

**Reasoning about topic COVERAGE rather than about entries** — deciding the stream half by "is every (address, topic0, range) I now need already inside what was fetched" — was rejected as unreachable, not as undesirable. A stored entry is an opaque digest, so a narrowed range cannot be recognised as a subset of a stored one; it reads as a new entry and invalidates the stream. That is conservative and therefore safe, and it is strictly better than the previous behaviour, which invalidated on any difference at all.

**Making the stream's kept `args` authoritative on replay** was rejected as unsound. A cached stream is two things at once: the raw log (`topics`, `data`, `address`), which is what the node said and is true forever, and `args` / `eventName`, which is what SOME ABI made of it. Only the first survives a source change, so `LogEventFetcher.reparse` decodes the stream AGAIN, against the source running now, before a single event reaches the processor. This is UNCONDITIONAL rather than "only when the decoding shape moved", because a stream file carries ONE context for events appended across several sources, so "was this event decoded under the current ABI" is not a question it can answer per event. Where a `logValues` projection dropped the raw log there is nothing to re-read, and the stream is CLEARED rather than replayed on trust.

**Refusing to read a context written by the shipped code, or silently trusting it,** were both rejected. `ContextIdentifier` is PERSISTED and the whole point of the change is to stop paying for regenerated ABIs, so an upgrade that re-indexed every existing deployment once would be the exact cost it removes, charged one last time. The block-0 entry therefore carries `legacyHash`, the whole-source digest the pre-per-event code persisted as its single entry, purely so that a stored context of that shape can be compared at all: equal means nothing moved and nothing is invalidated, unequal means the source moved and the old entry cannot say where, so both halves go from block 0 exactly as they did before. A context in the per-RANGE shape needs no bridge, because `hash` is computed exactly as it always was and matches byte for byte.

## Consequences

This SUPERSEDES the consequence of ADR-0033 that a source declaring no range keeps the single whole-source context entry. It no longer does; what keeps every stored context readable is the bridge above, and the first save after an upgrade rewrites the context as the per-event list, so the bridge is paid at most once per deployment.

`legacyHash` is deliberately NOT part of the identity invalidation is computed on, and it is the one field that moves when a regenerated ABI gains a view function — it has to, since it exists to be compared against a digest that committed to exactly those bytes. Byte-identity claims about a source whose events did not change are therefore claims about `{startBlock, hash, streamHash}`.

The entry list is SORTED (by `startBlock`, then by `hash`) rather than transcribed from the ABI array, which is what makes reordering the events in an ABI produce identical bytes and not merely an identical verdict.

`stream.valid` can never be true where `state.valid` would be false for a reason the filter can see: everything `streamHash` commits to is also committed to by `hash`, so nothing moves the filter without moving the decode. The implication runs one way only, which is the point.

An ANONYMOUS event contributes no `topic0` to `streamHash`, so two anonymous events at one address over one range share a stream digest. That is correct rather than a collision: neither is in a filter, so neither can grow one.

`WireContext` is untouched. `wireContextOf` still hashes the whole source into one entry, because it is an identity check between the two halves of a split deployment computing the same thing from the same declarations (ADR-0004), not a question about what a stored context covers. The server-side `StreamBuilder` therefore still gets the all-or-nothing answer, through the same code path, via the both-sides-legacy branch.
