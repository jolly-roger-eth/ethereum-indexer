# A generation pauses by CAPPING `toBlock` and DRAINING, never by truncating

An operator must be able to PAUSE a **generation** so it stops indexing without being deleted, and resume it later, **without it ever answering with state a reorg has invalidated underneath it** (`a-reconfigure-is-not-an-outage`, story 10). We decided that a pause sets `maxToBlock = x`, where `x` is the generation's cursor at that moment, and **nothing else**: the generation keeps being polled, fetches nothing above `x` but still re-scans the reorg window up to it, and goes idle by itself once `x` falls below `latestBlock - finality`. Nothing is truncated, nothing is reverted, `revertTo` is never reached on this path, and **no new mechanism is added** — the cap goes on `toBlock` before the existing `fromBlock > toBlock` guard, and the existing `getFromBlock` (`max(min(lastToBlock + 1, latestBlock - finality), 0)`) produces the whole behaviour: a SHRINKING re-scan while the cap is inside the finality window, then the existing "no new block" branch once it falls out of it.

The hazard this addresses is not hypothetical: a generation that simply STOPPED would carry an unconfirmed window it can no longer correct, so a reorg inside that window would never be found and its state would permanently contain events from blocks that no longer exist. Draining removes the hazard by waiting it out rather than by cutting it off.

## Considered Options

- **Truncate on pause** (drop the unconfirmed window, or `revertTo` a final block). **Rejected, and this is the decisive one:** story 4 wants the **canonical pointer** moved BACK to a generation to restore its answers EXACTLY, and a truncating pause changes those answers — so the two stories would contradict each other. It is also destructive and capability-gated at the storage seam, for a hazard that waiting out removes for free.
- **Stop the engine where it stands** (`disableProcessing()`). Rejected because that IS the hazard, not a way round it: the window is frozen with the state, and nothing ever re-scans it. `disableProcessing` remains what it always was — a stop, for a reconfigure or a teardown — and pause is deliberately a different verb.
- **A `paused` flag consulted by the indexing loop**, with a timer or a small state machine to decide when the drain is over. Rejected: it is a second copy of an answer `getFromBlock` already gives, and the copy can disagree with the value the loop acts on. `pauseState` is DERIVED from the cap and that same function, so `drained` is true exactly when the fetch loop takes its no-new-block branch.
- **Cap `lastSync.latestBlock` as well as `toBlock`**, which reads as consistency. Rejected because it silently breaks the whole thing: `getFromBlock` would then return `latestBlock - finality` forever, the cap would never fall out of the window, and the drain would NEVER idle. The cursor keeps tracking the REAL head; only `toBlock` is capped.

## Consequences

- **A pause is NOT INSTANT.** It completes after up to `finality` blocks of continued light polling, and only if the driver keeps calling `indexMore()` — a driver that stops the moment it pauses leaves the generation holding an unconfirmed window forever, which is the thing draining exists to prevent. `PauseState` (`running` / `draining` / `drained`) is published so a consumer can see the difference.
- **`unconfirmedBlocks` may still LIST blocks once drained, and that is COSMETIC.** The re-add rule compares against `lastToBlock`, and `lastToBlock` is frozen at the cap. Every block it lists is below `latestBlock - finality` and therefore final, so nothing it describes can be invalidated and nothing re-fetches to compare against it. Do not "fix" it by clearing the window: that would be the truncation this ADR rejects.
- **RESUME is removing the cap, and nothing else.** A reorg that struck below the cap while draining was already corrected; one that struck above it is re-derived on the first uncapped round, because `getFromBlock` re-scans from `latestBlock - finality`.
- **A FOLLOWER cannot be paused this way and is REFUSED** (`CannotPauseFollowerError`). A cap governs the verb that FETCHES, and a follower fetches nothing: it advances exactly as far as the stream it folds (ADR-0044), so a cap would sit on a verb that never runs and `pauseState` would report a drain that is not happening. A pause that lies is worse than a refusal here, because the whole value of `drained` is knowing that nothing invalidatable is still being answered.
- **Pausing a stream's WRITER stops every follower on that stream**, which ADR-0044 already predicted. It also has a sharper edge worth naming: the follow path advances on the stored cursor's `lastToBlock`, and a paused writer's `lastToBlock` is frozen at the cap, so a retraction the writer discovers DURING its drain is appended to the stream but does not move that cursor — and a follower can therefore miss it. That is the follower path's guard, not the cap, and closing it belonged to the follower path: it is CLOSED by ADR-0049, which replaced that guard's cursor comparison with a question asked of the stream's own emissions. The cap is unchanged.
- **A pause is IN MEMORY and is not recorded in the registry.** The registry holds what a generation IS; a pause is what one is DOING. A reload comes back running, which costs one more drain to re-pause and never costs correctness. Making it durable is a registry record, to be added when something needs it.
