# The sync cursor lives behind the storage seam, as an opaque string written with its block

`StateStore` gains a small cursor port — `readCursor` / `writeCursor` / `clearCursor` over an **opaque string** under a caller-chosen key, plus an optional third argument to `applyBlock` — and `LastSync` persistence moves out of `@etherfold/processor-sqlite`'s `_sync` table into whichever backend a deployment chose. This reverses an explicit non-decision: `store.ts` listed the sync cursor under "deliberately absent", on the grounds that where a processor keeps its cursor is the processor's business (ADR-0016).

That reasoning was right about the MEANING and wrong about the STORAGE, and two things said so.

**A cursor that can only be a SQL table stops "one processor, several backends" at the first deployment that is not SQLite.** A browser tab on IndexedDB has no SQL to write one into. Every alternative home keeps that problem: it just moves the per-deployment wiring somewhere else.

**Only the store holds the transaction the block write happens in.** The cursor used to be a second round trip after `applyEventStream`, and the window between them was not self-healing. A crash there left state ahead of the cursor; the restart resumed from the stale cursor, re-fetched blocks it had already applied, and `applyEventStream` only reverts when a stream carries a retraction — a plain replay has no fork point, so nothing reverted and `applyBlock` was handed a block the store already held. Every backend refuses that by design, correctly, because silently re-applying would double-write versions. The indexer therefore did not merely redo work: it threw on every subsequent start, and no amount of restarting cleared it. That was `work/notes/observations/sync-cursor-write-is-not-atomic-with-the-block-it-describes.md`, deleted with this change because it stopped being true.

## Why an opaque string, and why the port stays this small

`LastSync<ABI>` is a `@etherfold/core` type carrying `EventBlock<ABI>`s of decoded events. Typing the port with it would make `@etherfold/state-store` depend on core, invert ADR-0016's direction and drag viem into every storage primitive — exactly what ADR-0018 exists to prevent and what `state-store-sqlite/test/no-platform-leakage.test.ts` pins. So the store persists a string and knows nothing about what it means; the codec (`serializeLastSync` / `deserializeLastSync`, plain JSON with a bigint tag) was already neutral and moved to `@etherfold/processor-entities` unchanged. ADR-0016 is intact: a processor package still names where its state lives, and a store still cannot tell an indexer from any other caller.

The KEY is a name, not a `ContextIdentifier`. The neutral processor writes one fixed key on purpose: the core's discard-and-clear branch lives inside `if (loaded)`, so a cursor keyed by context would answer "nothing stored" after a processor upgrade and the new run would index on top of the previous processor's rows. The context travels INSIDE the value, where the core already validates it.

## Considered options

- **A separate cursor keeper the deployment supplies.** Not the existing `KeepState`, which persists `{state, lastSync}` together and would store the state twice here, so it would be a NEW narrower interface: a second thing to wire per deployment, a new way to misconfigure (a store pointed at one database and a keeper at another, diverging in silence), and — decisively — no atomicity, because a keeper cannot join a transaction it cannot see. Worth noting what the bundling in `KeepState` is FOR: a single keyed write of `{state, lastSync}` is how the free-form path gets the very atomicity this buys with a transaction. Same invariant, different mechanism, because a blob has no transaction to join.
- **A reserved entity through the existing seam.** No new API, but the cursor would become versioned, revertible and prunable entity state — and it must survive exactly the operations that would destroy it.
- **Making replay idempotent instead of atomic**, by having the processor skip blocks the store already records. That trades a crash-consistency guarantee for a tolerance and weakens a check that currently catches a real caller bug, so it is the worse answer wherever the atomic route is available.

## Consequences

- **Every backend inherits the obligation**, and the contract now carries something that is not entity state. It costs a handful of lines each (one table, one object store, one `Map`) and the shared conformance suite makes it an obligation rather than a convention, including the case that matters: a store never reports a cursor ahead of the last block it applied.
- **The cursor is per BLOCK, not per `process` call.** One `process` carries many blocks and each is its own transaction, so writing the stream's cursor with the last block alone would leave the same window open for the whole run. Each block is applied with the cursor that describes IT (`syncedThrough` truncates `lastToBlock` and the unconfirmed window; the observed chain tip is not truncated), and the last block carries the stream's own. A stream with no blocks still moves the cursor, through `writeCursor`, because a scanned range that carried none of our logs is progress and a crash there costs a re-scan rather than a wedge.
- **The cursor is not reverted.** `revertTo` leaves it alone: how far the CALLER got is not entity state, and the caller moves it when it applies the canonical branch, which arrives in the same stream as the retraction.
- **A snapshot bootstrap gets the atomic install it needs for free.** Rows and the cursor they belong to land as one unit through `applyBlock(block, rows, cursor)`. What it does NOT yet give is a bootstrapped store reporting a retention floor it did not compute: retention is configured as a distance from the tip, and a snapshot of current rows needs an ABSOLUTE floor at the snapshot block. That is `bootstrap-an-entity-store-from-a-snapshot`'s to add.
- **On SQLite the storage moved**, from `@etherfold/processor-sqlite`'s `_sync (id, lastSync)` to `@etherfold/state-store-sqlite`'s `_cursor (key, value)`. The new table is neutral in its names as well as its dependencies: there is no `lastSync` column in a storage primitive. Nothing in this repository is published under the `@etherfold` scope yet, so no migration is written; an existing database reads as never-synced and re-indexes.
