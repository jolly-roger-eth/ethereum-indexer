# CONTEXT — etherfold domain language

The domain glossary for `etherfold`. Agents and skills use THIS vocabulary when naming modules, tests, and discussing the system. Architectural rationale lives in `docs/adr/` (decisions); product framing lives in `work/specs/`.

## What etherfold is

A modular, TypeScript indexer for Ethereum and other EIP-1193 / JSON-RPC chains that turns a contract's event logs into a derived application **state** via a **processor**, and can run either fully in-browser (client-side indexing over EIP-1193, no server) or server-side. It supports reorgs, caching, and hydrating clients from pre-computed snapshots instead of indexing from scratch.

## Core domain terms

- **IndexingSource** — what to index: `chainId`, the contracts (`abi`, `address`, `startBlock`), optional `genesisHash`. Hashed into the sync context so a source change invalidates stale state.
- **source hash entry** (`SourceHashEntry`, the elements of `ContextIdentifier.source`) — the UNIT invalidation is decided on: one entry per (contract, event, live range), over a leading SKELETON entry at block 0 carrying what an ABI cannot describe (`chainId`, `genesisHash`, each contract's `address` and `startBlock`). Per EVENT whether or not the source declares ranges, because an ABI is REGENERATED and not hand-edited, so what moves in it most often is what nothing depends on: a non-event member (a function, an error, a constructor) contributes to NOTHING, a reorder produces identical bytes (the list is SORTED, not transcribed), and a recompilation that only spells `internalType` differently is invisible because the digest is over `decodingShapeOf`. The rest of the source is NOT free and still invalidates everything. An entry carries TWO digests, because the fetch and the fold do not depend on the same thing (ADR-0034), plus `legacyHash` on the block-0 entry alone: the whole-source digest the pre-per-event code persisted, kept purely so a stored context of that shape can be compared instead of re-indexing every existing deployment once. `legacyHash` is deliberately NOT part of the identity, so "a source whose events did not change hashes byte-identically" is a claim about `{startBlock, hash, streamHash}`.
- **the STREAM verdict and the STATE verdict** (`SourceInvalidation`, `streamMatches` / `stateMatches`) — the TWO answers `sourceInvalidationOf` gives, never one. The **stream** is raw logs fetched under a topic-and-address filter, so it survives everything that did not GROW that filter: a shrunken topic set leaves a strict SUPERSET, which is reusable by decoding less, and a removed event therefore keeps it. The **state** is a fold over DECODED events, so it dies whenever the decoding shape moved, even where not one log needs re-fetching. A renamed non-indexed parameter is the case that proves they are two questions: `topic0` hashes types and not names, so the fetch is untouched and the decode is not. Both halves keep `invalidFromBlock` (the block they are invalid FROM), because the decision naming a block is what lets a reconfigure be a REFINEMENT rather than a rewrite (`work/specs/proposed/a-reconfigure-is-not-an-outage.md`); neither collapses to a boolean. The comparison is a SET DIFF over digests rather than element-wise by index, since an un-ranged source puts every event at the same block and an insertion would otherwise shift the list. What is kept when the stream survives is only its RAW half: `LogEventFetcher.reparse` decodes a replayed stream AGAIN against the source running now, because the stored `args` are what SOME earlier ABI made of those bytes.
- **event block range** (`RangedAbiEvent`'s `firstBlock` / `lastBlock`, `@etherfold/core`) — the span of blocks ONE ABI event is live over, both bounds INCLUSIVE, `lastBlock` omitted meaning open-ended. An event is not a fact about a contract, it is a fact about a contract over a range of blocks, and saying so is what lets an upgrade APPEND an entry describing only the blocks above the cursor, which `sourceInvalidationOf` reads as "this could not have contributed yet" and therefore keeps both the state and the cached stream. It is used for INVALIDATION (as the range half of a **source hash entry**, above) and for WHICH TOPICS a fetched range requests (a range carries only the events whose declared ranges intersect it, unioned per `topic0` across contracts, and issues no `eth_getLogs` call at all where no declared event can occur; an event that DECLARES no range is open-ended from block 0 there, never narrowed on its contract's `startBlock`, so every omission follows from a declaration) and for NOTHING ELSE: decoding is by `topic0` with no block axis, because the boundary is unknowable in advance and not block-granular anyway (the upgrade transaction sits mid-block), and a true `topic0` collision is refused rather than resolved by a boundary — ADR-0033 on top of ADR-0031. Deliberately NOT `startBlock`, which means "do not look before here" per CONTRACT and is MINIMISED across them by `defaultFromBlockOf`. For an upgrade at block `b` the CORRECT declaration is `A.lastBlock = b` together with `B.firstBlock = b`, the same number twice, because a transaction earlier in `b` still fires A; the one-block overlap is preserved, and an exclusive end would make the obvious thing to type lose the pre-upgrade logs in `b`. Ranges are NORMALISED before anything reads them (an open-ended occurrence absorbs the rest from the minimum `firstBlock`; otherwise the union), so the redundant entry a generator appends when it cannot recognise a rollback costs nothing; a GAP between two ranges of one event is REFUSED at construction, because a hole is a span nobody requests. A source declaring no range REQUESTS exactly what it always requested, topic for topic, since nothing narrows until something declares; what it no longer does is hash WHOLESALE, because invalidation is per event either way (ADR-0034 on top of ADR-0033).
- **EventProcessor** — the reducer contract the core drives: `load` / `process(eventStream, lastSync)` / `reset` / `clear` / `getVersionHash`. Given a stream of events, it produces the derived `ProcessResultType` state.
- **JSObjectEventProcessor** (the path that SHIPPED; **NOT the target**) — the in-memory JS-object reducer authored via `fromJSProcessor(...)` (`on<EventName>` handlers). It is what stratagems-world → stratagems-snapshots runs today, via `@etherfold/browser`, and it is **ON ITS WAY OUT** (ADR-0037): `work/tasks/backlog/retire-the-js-object-processor-path.md` deletes the package and the free-form authoring path once `index-to-a-store-from-the-cli` has moved the CLI off it. Until then it works and nothing new should be built on it. But the **ENTITY path** (`EntityProcessor` / `EntityEventProcessor`, the whole of `work/specs/tasked/one-processor-everywhere.md`) is what this project is FOR, and effort is weighed accordingly: a capability delivered only to the JS-object path is worth less than the same capability on entities, and a design that serves entities well and the blob path adequately is the right trade rather than a compromise. Reorg revert here is `History.reverseBlock` (immer reverse-patches); on the entity path the store owns it.
- **LogEvent** — a decoded (or parse-failed) log with block/tx coordinates; carries `removed: true` when an event is reorged out.
- **LastSync** — the sync cursor: `latestBlock`, `lastFromBlock`, `lastToBlock`, the `context` hashes, and `unconfirmedBlocks` (the recent, reorg-eligible window).
- **reorg / removed / finality** — the reorg model. `generateStreamToAppend` (core engine) shapes the fetched logs into an append stream, emitting `removed: true` markers for reorged-out blocks and pruning `unconfirmedBlocks` past the finality window. Processors consume that stream and revert-then-reapply. (Contract pinned by `packages/core/test/utils.test.ts` and `packages/js-processor/test/reorg.test.ts`.)
- **stream / keepStream (ExistingStream)** — the cached raw event stream seam, so a client can resume/re-derive without refetching all logs.
- **segment / scanned extent** (`work/specs/tasked/appending-to-the-stream-costs-the-batch.md`, ADR-0035) — how a cached **stream** is stored: an append-only run of **segments** keyed by an ORDINAL index, one per batch, never rewritten, so a save costs its batch and not the history. Ordinal and not block-ranged because the stored stream is an EMISSION stream, so a reorg re-appends superseded events at their ORIGINAL block flagged `removed` and a LATER segment can hold LOWER blocks — ranges overlap, cannot key anything, and no segment may be skipped on a block bound (segmentation is a WRITE-path optimisation; the read stays a full ordered scan). A segment is `{events}` and nothing else: the three block numbers and the `context` live once, in the CURSOR RECORD beside the segments. An earlier design put a per-segment scanned extent there to let a truncated prefix resume; that recovery is withdrawn, and an inconsistent stream (a gap, a cursor without segments, an unparseable segment) is CLEARED and rebuilt rather than repaired. **No segment and no cursor record stores `unconfirmedBlocks`**: the window has two homes that are read (the state keeper's saved `lastSync`, and the entity path's serialized sync cursor) and a stream keeper's copy is read by nobody, which `captureStream` and `replayStream` already demonstrate by persisting an empty one. A stream is addressed HIERARCHICALLY — `['stream', <indexer-name>, <streamDigest>, <ordinal>]`, as ARRAY keys on IndexedDB, columns on SQL — so enumeration is a SCOPED KEY-RANGE read and never a pattern match over a flat namespace. `chainId` is deliberately NOT an address component: it is already inside the stream digest via the block-0 skeleton entry. The CURSOR is addressed within its stream's subtree, so a scoped delete removes it with the segments and `clear` cannot orphan one. A GAP in the ordinals is CLEARED along with the rest of the stream: inconsistency is not repaired. A CURSOR WITH NO SEGMENTS is not inconsistency though — it is a stream that has been scanned and found nothing yet, and clearing it would re-scan from the start block on every reload. (Filesystem stream storage is deliberately NOT supported, and the *tail* and *seal* it needed are gone with it; OPFS is the plausible next file-shaped keeper and would ride the same seam.)
- **StateStore** (the STORAGE SEAM, `@etherfold/state-store`) — what a store must do for a processor to run on it: `migrate` / `applyBlock` / `getCurrent` / `getAsOf` / `listCurrent` / `listAsOf` / `revertTo` / `prune` / `readCursor` / `writeCursor` / `clearCursor`, plus the capabilities it declares. Implemented by `@etherfold/state-store-sqlite` (versioned rows over `remote-sql`), by `@etherfold/state-store-indexeddb` (versioned rows in IndexedDB: the BROWSER DEFAULT, decided as a condition in ADR-0024 and selected through `createBrowserStateStore` in `@etherfold/browser`), by `MemoryStateStore` (the reference implementation), and by `@etherfold/state-store-patch` (the LIGHT store: current state as a plain object, history as immer reverse patches, so it declares `revert-only` and `durability: 'memory-only'`). Block addressing by hash or time, and any richer query surface, sit ABOVE the seam and are a backend's own.
- **entity declaration** — `{name, id, fields}`, the whole per-entity contract an author writes. The store owns everything else: the layout, the version columns, the as-of read and the reorg revert. Whether a declaration is LEGAL is a fact about the declaration and not about the backend: the identifier rules (ASCII shape, the store's `_` namespace, and case-insensitive uniqueness across entity names and across the columns of one row) live at the seam and are refused at DECLARATION time, on every backend. A genuinely engine-specific limit (SQLite's `sqlite_` namespace) is refused by that backend, also at declaration time and never at `migrate()`. The one thing no backend may do is accept a declaration and then diverge or die later.
- **version** — one COMPLETE row of an entity with a half-open block-validity range (`_lower` inclusive, `_upper` exclusive, NULL meaning live). `set` writes a whole row, so an unlisted declared field becomes NULL; `delete` closes the live version without opening a new one.
- **MutationContext** — the write surface a handler gets for ONE block (`get` / `set` / `delete`, plus `update` as sugar over get-then-spread-then-set), with read-your-writes inside that block. Uniformly async on every backend. It carries exactly one SET read, the **listing** below. A row read back inside the block that wrote it has the same shape as one read a block later (id columns present, an unlisted declared field NULL): `get` and `list` build a staged row through one construction, so the shape of a row never depends on when it was read.
- **listing** (the bounded id-prefix listing, `MutationContext.list` / `StateStore.listCurrent` / `listAsOf`) — the rows whose declared id starts with a **prefix** (a LEADING run of that entity's id columns, at least one of them), ascending in the id's own order, bounded by a REQUIRED limit, answered as `{rows, truncated}`. Never a predicate, a caller-supplied ordering or an offset: the bound is the decision (ADR-0021), because a handler runs once per event on every backend and a key-prefix range with a limit is the one shape that is an indexed range scan everywhere. It is how a one-to-many is read (children keyed by their parent, collection DERIVED WHEN READ, like a subgraph's `@derivedFrom`), so it costs nothing at write time. Order is lexicographic over the stringified id, so a numeric key must be fixed-width. Distinct from a backend's own richer read surface (`queryCurrent` / `queryAsOf`, caller-supplied SQL), which sits ABOVE the seam where a query planner exists.
- **read surface** (`createReadSurface`, `@etherfold/state-store`) — the reads GENERATED from a set of **entity declarations**, so a consumer names an entity and its declared columns instead of a table and a column string, and a renamed field breaks compilation rather than returning `undefined`. It is the same four reads the seam has (`getCurrent` / `getAsOf` / `listCurrent` / `listAsOf`), typed off the declaration by `declareEntities` (an identity function that keeps the literal types an annotation would widen away), with rows PROJECTED to the declared columns (version columns dropped, an unlisted field `null`) and nothing decoded beyond the declared storage class (ADR-0025). Its as-of parameter is whatever ITS store takes, so a hash reaches a backend that resolves one and does not compile against a backend that does not. Its SERVER-side tier is **`createQuerySurface`** (`@etherfold/state-store-sqlite`): the same four plus `queryCurrent` / `queryAsOf`, which take caller-supplied SQL. Two tiers, one schema source; the split is the same one ADR-0021 makes, because a handler runs once per event on every backend and a server-side reader does not. Distinct from the untyped, entity-name-string read handles `process()` hands back, which split on the same line: **`EntityStateView`** (`@etherfold/processor-entities`) has the seam's four reads and the capability report, and **`VersionedStateView`** (`@etherfold/processor-sqlite`) has those plus `queryCurrent` / `queryAsOf` and block addressing. The SQL pair is absent from the neutral handle rather than stubbed to throw, so asking a backend-neutral handle for a backend-specific read is a COMPILE error in the editor instead of a runtime throw in a browser tab.
- **sync cursor** (the CURSOR PORT, `StateStore.readCursor` / `writeCursor` / `clearCursor`, and `applyBlock`'s third argument) — how far a processor has got, kept BEHIND the storage seam as an **opaque string** under a caller-chosen KEY (ADR-0027). The string is a serialized `LastSync`, and the store knows nothing about that: typing the port with `LastSync<ABI>` would make `@etherfold/state-store` depend on core and invert ADR-0016, so the codec (`serializeLastSync` / `deserializeLastSync`, `@etherfold/processor-entities`) sits above it. It is at the seam and not in a keeper because only the store holds the transaction the block write happens in, so only the store can write the cursor in the SAME transaction as the block it describes; the two used to be separate round trips and the window between them wedged an indexer after a crash. The KEY names WHICH cursor and is NOT the `ContextIdentifier`: the neutral processor writes one fixed key (`SYNC_CURSOR_KEY`) and the context travels inside the value, because the core's discard-and-clear branch only runs when `load` returns something. The cursor is deliberately not versioned, not reverted and not pruned: how far the CALLER got is not entity state.
- **EntityProcessor** (`@etherfold/processor-entities`) — a processor written against the seam: entity declarations plus `on<EventName>` handlers over a `MutationContext`, naming no backend. `JSObjectEventProcessor` is the same role over a free-form object.
- **EntityEventProcessor** (`@etherfold/processor-entities`) — the `EventProcessor` the core drives that runs an **EntityProcessor** against ANY `StateStore`: the store is INJECTED, so the same processor definition indexes to SQLite on a server and to IndexedDB in a browser with nothing about the processor changed. Revert-then-apply, the block grouping, the version hash and the sync cursor live here ONCE. **`VersionedStateEventProcessor`** (`@etherfold/processor-sqlite`) is now a thin SQLite flavour of it: it builds the store from a `RemoteSQL` and substitutes the SQL-tier read handle, and holds no indexing logic of its own.
- **processor kind** (`ProcessorKind`, `@etherfold/browser`) — WHICH of the two authoring paths a browser deployment is running, said by the caller as a TAG rather than sniffed: `'js-object'` (a **JSObjectEventProcessor**: the object IS the state, and a **KeepState** keeper persists the whole of it in one keyed write, which is how THAT path gets atomicity, since a blob has no transaction to join) or `'entities'` (an **EntityEventProcessor**: the state is rows in a **StateStore** the application chose, and the **sync cursor** rides in the block's transaction, ADR-0027). `createIndexerState` takes either — a `TaggedProcessor`, or a bare `EventProcessorWithInitialState`, which means `'js-object'` and is the form that shipped. Both kinds are `EventProcessor`s, so a runtime check for `createInitialState` would be a guess a wrapper or a proxy can make wrong in silence; the tag is checked by the compiler at the call site instead. A `keepState` on the entity path is REFUSED rather than ignored, because its store already persists both halves. The `'js-object'` kind is RETIRING (above), so this fork is expected to collapse to one kind.
- **retention** — how far back superseded versions are kept, measured in BLOCK NUMBERS and in no other unit (never a duration, never a count of updates: ADR-0019). Its floor is the finality depth, because reorg revert already requires that much. A deployment SETS it (`'revert-only'`, `{blocks: N}`, or `'unbounded'`) and a store REPORTS what it actually provides, so a caller discovers at startup what history is available instead of from a wrong answer. Note the trap: a window of N BLOCKS is not N updates of history (median 429 blocks between event-bearing blocks on the real measured stream).
- **prune** (`StateStore.prune`) — enforcing **retention** against STORAGE rather than against answers. A window bounds what a read may ask about from the moment it is configured (`assertRetained`); `prune` is what physically drops the versions it no longer covers, at the same boundary (`retentionFloor` is `retainedRange(...).from`, so the two cannot drift). It is an EXPLICIT call the host schedules and never a side effect of a write, because it costs time proportional to what it drops (ADR-0022); it is a no-op where there is no floor; and the LIVE version of an entity survives it however old it is, because that row is the current state. Distinct from the two other prunes in this repo: the core prunes `unconfirmedBlocks` past the finality window, `History` prunes reverse-patches by block distance, and the (unbuilt) `snapshot-prune-script` prunes orphaned CLI snapshot FILES, which is a different object entirely.
- **bootstrap** (`openSnapshotAware` / `StateSnapshot`, `@etherfold/state-store`; `bootstrapFromSnapshot` / `openAndBootstrap`, `@etherfold/processor-entities`) — starting a store from state somebody ELSE computed instead of replaying the chain from the start block. A **snapshot** is `{format, processor, savedAt, takenAt, cursor, rows}` where `rows` are the rows that are LIVE at `takenAt` (current rows only, measured: ADR-0028), and the rows and the cursor install as ONE `applyBlock` because a client that crashed mid-install must not come up holding rows it cannot account for. Same word, two shapes: the free-form path's snapshot is the whole state blob in the CLI's file envelope, and this is its entity-path counterpart. What has no free-form counterpart is the honesty a blob does not need, because a blob has no history to lie about: a snapshot carries NOTHING below its own block, so a bootstrapped store reports its **retention** as a window whose oldest block is the snapshot's (its **snapshot origin**, persisted under a second cursor-port key so a RELOAD is as honest as the first run), refuses an as-of read below it with `BlockNotRetainedError`, and refuses a revert reaching under it with `RevertBeyondSnapshotError` — which is deliberately NOT a `BlockUnavailableError`, on the same ground as `RevertBeyondPatchHistoryError`: that family is about a read this store cannot answer, and this is the write path, where the reorg was not undone. Client-side selection is the free-form keeper's, point for point (several locations, most advanced wins, prefer local when local is ahead, fail over on error), plus two things it does not do: it walks every remaining candidate on failover, and a snapshot from another **processor version** is not a candidate at all. PUBLISHING snapshots is deliberately out of scope (`work/notes/ideas/publishing-snapshots-of-versioned-state.md`); `createSnapshot` is the minimal producer the tests need, and it cannot read rows out of a store because the seam has no "list everything" read (ADR-0021).
- **BlockUnavailableError** — the family of "this store cannot answer about that block", ADR-0015 and ADR-0019. `NoSuchBlockError` (the address resolves to no recorded block) and `BlockNotRetainedError` (the block is fine, the versions are outside retention) are its two members. Neither is ever an empty result or a tip read: an as-of read served from the tip is a plausible wrong number nothing downstream can tell apart from a true one. Deliberately NOT a member: **`InvalidBlockNumberError`** (a `TypeError`, thrown by `assertBlockNumber` inside `assertRetained`, and by the SQLite addressing layer's height axis), because every member of the family is a fact about the STORE that a caller answers by re-pinning or widening retention, while an `at` that is not a whole non-negative number is a fact about the CALL that no store configuration makes answerable.
- **conformance suite** (`@etherfold/state-store-conformance`) — the one suite a **StateStore** backend must pass to earn its place behind the seam, parameterised by a factory. It asserts EXTERNAL behaviour only (what a read returns after a write, after a revert, as of a block), never a table, a statement or a version column, so a versioned-rows backend and a patch-log backend can both be asked it; and it reads a backend's declared **capabilities** first, so each backend is tested against its own CLAIM. Its cases are data (a `{group, name, run}` list) with the vitest registration as a thin adapter, which is what lets deliberately-lying backends be asserted to FAIL it (ADR-0020). Distinct from a conformance WORKLOAD, below.
- **conformance workload** — a SUBJECT fed to the backends the conformance suite covers, as opposed to the suite's own questions. Two exist: the small hand-written declarations inside `@etherfold/state-store-conformance`, and the heavy one, **`@etherfold/conformance-workload-stratagems`** (its own package, `private` and never published because its vendored oracle is GPL-3.0 and the port is a derived work of it: ADR-0026), which replays 31,332 real logs from the LAUNCHED stratagems game on Base through the ported processor and compares against the state that game's ORIGINAL `JSProcessor` computed from the same bytes. Its parts are a golden INPUT (a committed `StreamFixture`), a golden OUTPUT (the oracle's state; a diff on it means the processor changed meaning, which is a FINDING and not a fixture update) and an equality oracle that is not our own reimplementation. Note the trap it carries a label for: stratagems has two deployments on Base and `deployments/base` is the ABANDONED one (45 logs), while `deployments/alpha1` is the launched game.
- **tx inclusion** (`checkTxInclusion`, `@etherfold/core`; `createIndexerState(...).checkTxInclusion`, `@etherfold/browser`) — whether the state a client is about to render already accounts for a given transaction, which is what an app must know before it lays an OPTIMISTIC update over indexed state: applied on top of a state that already contains it, a non-idempotent update (a counter, a balance, an append) is counted twice. Answered from `LastSync.unconfirmedBlocks` and NOTHING ELSE stored: the window already holds whole blocks with their events, every event carries its `transactionHash`, and the set maintains itself under reorg because a reorged-out block leaves the window. Deliberately NOT answered by comparing the caller's receipt: a block HEIGHT is a local opinion about a chain rather than an identity, and the receipt's block HASH is the wrong identity, since a reorg can re-include the same transaction in a different block, so a hash comparison reports "not indexed" for a transaction that IS indexed, which is the double-count it was meant to prevent. The question is about the indexer's own chain, so only the indexer answers it. Two things make a verdict rather than one: a window hit must ALSO be behind `lastToBlock`, because `feed` publishes the whole new window and only then walks the cursor through it, so presence is not application. Its two documented limits both follow from the window being SPARSE (event-bearing blocks only): a transaction that emitted nothing indexed can never hit (`work/notes/ideas/tx-inclusion-for-a-tx-that-emitted-no-indexed-event.md`), and `absent` means "not in the window", so the caller must not ask about a transaction older than it — which one it just submitted cannot be. The optional `minedAtBlock` closes both for a caller that has a receipt, through the `below-window` branch, which rests on the same finality assumption the indexer already makes when it prunes.
- **KeepState** — the persisted-state seam (`fetch`/`save`/`clear`) backing in-browser (IndexedDB/localStorage) and fs storage adapters; also how snapshots hydrate a client.
- **createAction** — the internal promise-serialization primitive in the core `EthereumIndexer` (`_index`/`_feed`/`_load`/`_save`) that keeps overlapping load/feed/index calls from interleaving.
- **work/ contract** — the on-disk system this repo uses, defined by the reference docs in **`work/protocol/`** (copied here by `setup`). Three REGIME umbrellas — `notes/` (capture buckets: `observations`/`ideas`/`findings`), `tasks/` (the build board: `backlog`/`ready`/`done`/`cancelled`), `specs/` (the spec lifecycle: `proposed`/`ready`/`tasked`/`dropped`) — plus top-level `questions/` and `protocol/`. One markdown file per item, status = the folder it lives in (never a field). ADRs (`docs/adr/`, format in `work/protocol/ADR-FORMAT.md`) record what WE decided and why.

- **generation** (`work/specs/proposed/a-reconfigure-is-not-an-outage.md`) — ONE indexed lineage: a **stream** plus a fold over it. Identified by its STREAM plus the processor's `version` hash — the config hash is already inside the stream digest, so naming it again would be redundant. A PROCESSOR change is therefore a new generation over the SAME stream (and re-fetches nothing) while a FILTER or CONFIG change is a new stream. An indexer holds several; one is canonical. The word is deliberate and every obvious alternative is taken: `version` already means an entity row's half-open block-validity range AND a processor's `version` field (which is an INPUT to a generation's identity, so the same word would mean two things one sentence apart), `deployment` already means the fetcher/server topology and a browser installation, and `candidate` is taken by the entity snapshot path. Reconfiguring CREATES a generation instead of discarding state; **blue-green** (ADR-0008) is the two-at-a-time special case of the same mechanism.
- **stream identity** — a stream is identified by its FETCH FILTER, never by who indexed it: a wide synchronous digest over the DEDUPLICATED `streamHash` values SORTED BY `streamHash` (address, `topic0`, range — see **source hash entry**), PLUS the stream CONFIG hash. Both halves matter. Sorting by `streamHash` rather than taking the entry list in its own order is load-bearing: that list is sorted by `(startBlock, hash)`, and `hash` covers the DECODING shape, so a decode-only change reorders it and a digest over that order would fork a new stream and re-fetch everything. The config belongs because `sourceInvalidationOf` invalidates the STREAM from block 0 on a config mismatch, and `alwaysFetchTimestamps` and `alwaysFetchTransactions` each change what is STORED. `parse` belongs too, on the strength of `parseConfig.filters`, which narrows which events are parsed and kept at all. (`parse.logValues` was a third reason and is DELETED with the knob by `work/specs/proposed/the-stream-stores-only-what-the-node-said.md`: an unused stub whose only purpose, reducing what is stored, that spec removes. Nothing about this hash needs narrowing as a result.) This is ADR-0006's `{source, config}` stream keying made concrete, narrowed on the source side to the FETCH half per ADR-0034. Not `simple_hash`, which is 32 bits: as a change DETECTOR a collision costs one missed invalidation, but as a KEY it means one generation silently adopting another's stream under a filter that does not match it. Two generations may READ one stream; only the one indexing WRITES it.
- **exploration spec versus build spec** (`work/protocol/TASKING-PROTOCOL.md` §2a) — the two SPEC KINDS, distinguished by what DONE means. A **build spec**'s done is the capability SHIPPED, tasked atomically as vertical tracer-bullet tasks. An **exploration spec**'s done is CONFIDENCE plus a de-risked, sliced BUILD PLAN: its stories are reach-confidence stories (pin the seam, spike the risky part on the narrowest real case, resolve an open question into a decision, emit the plan), and the capability build becomes a FOLLOW-ON build spec ordered by `taskedAfter`. The reframe is what stops a too-uncertain ambition being tasked as FICTION — build tasks written against a seam nobody has chosen. `a-generation-can-be-seeded-from-a-published-artifact` is the worked example: it was a build spec whose Implementation Decisions read "None yet, deliberately" and two of whose four questions were seams that do not exist. An exploration spec is still just a spec in `work/specs/`, tasked atomically like any other; it adds no folder and no status.
- **generation cap** (`maxGenerations`, `maxStreams`) — a COUNT of generations or streams an indexer may accumulate, which REFUSES at the bound rather than evicting. Deliberately NOT called *retention*: **retention** is pinned below to a distance in BLOCK NUMBERS and ADR-0019 refuses a second retention mode measured in anything else. The two meet in one config object — every generation HAS a store WITH a retention window — so they must not share a word.
- **indexer** (the NAMED unit; the server and CLI multi-tenancy unit) — one indexed **answer set**: a set of generations and streams over ONE chain, holding ONE **canonical pointer**, carrying the **generation caps**, and fully isolated from every other. An indexer-server or a CLI hosts SEVERAL, each under a NAME the operator supplies on `upload`; a BROWSER APP may also run several, naming them itself. **The name is UNIVERSAL, not a server-only concept** — one discriminator, two sources of its value — and it is the top level of the stream address everywhere, so no runtime needs an extra one. The browser case is not hypothetical: an app watching several accounts (an NFT viewer) names one indexer PER WATCHED ADDRESS, which is the right modelling because those datasets are PARALLEL and equally valid, with no canonical among them. Do NOT model that as generations: a **generation** is an EVOLUTION of one logical thing with ONE canonical answer, so a filter that identifies a different subject is a different INDEXER, while a filter change that refines the same subject is a new generation of it. The discriminator is STRUCTURAL, part of a composite key every server-side read and write takes, never a field a query may omit and never defaulted — the same hazard class the client side removed by addressing a stream HIERARCHICALLY rather than packing its components into one delimited string, where a discriminator a read can omit, or one packed so that something else can be mistaken for it, silently answers with another tenant's rows.

  **The word is deliberate, and what it REPLACED matters more than what it beat (ADR-0036).** An earlier design called this a *project* and treated it as a second axis ABOVE the indexer. That axis was deleted rather than renamed, because once an indexer is one chain and one answer set the two units are THE SAME THING, and the glossary already said so in every place that counted: an indexer holds several generations, one is canonical, and the caps are per indexer. `instance` was rejected as filler that implies a running copy (this persists with nothing running), `dataset` as inventing a word where one existed, and `deployment` was already taken twice over. The residual cost, accepted: `EthereumIndexer` (the class) is one source plus one processor plus one state, which is a GENERATION rather than the container, so that class is renamed when the container lands.

  **One name is one chain at a time.** `chainId` is NOT an address or key component anywhere — not in the client's stream address, not as a column on the server's emission table — because it is already carried inside the STREAM identity both are keyed on (its block-0 skeleton entry hashes `chainId` and `genesisHash`). Two chains therefore produce different stream digests and cannot collide, with no guard needed. It is not an identity axis in its own right: changing an indexer's chain changes `chainId` and `genesisHash` in the block-0 skeleton entry, hence the source hash, hence the STREAM — so it is an ordinary reconfigure that makes a new generation, with the old chain's generation retained under the caps and revertible. Two chains you want live SIMULTANEOUSLY are therefore two names, because under one name the second would be read as a successor and not a sibling. Two contract deployments on ONE chain are likewise two names, since a single canonical pointer can only name one generation (stratagems' `alpha1` and the abandoned `base` are the worked example). Whether the discriminator maps to a shared table with a column, a table prefix, or a schema is a storage-ADAPTER decision, and it stays one only because the key is composite.
- **canonical pointer** — the single record naming which **generation** answers reads. Moving it IS promotion and moving it back IS revert; it is one small write, which is why promotion has no meaningful cost. Its policy has three values and ONE default everywhere: **`on-catch-up`** (the default — the pointer moves when the successor reaches the canonical generation's cursor), **`immediate`** (canonical on creation, before catching up; OPT-IN, for a developer who wants to see what an edit did) and **`manual`**. There is deliberately NO per-environment default: that would need a development-versus-production distinction, and nothing in a browser build can detect one, so the safe value is the default and the unsafe one is chosen explicitly. Reads RE-RESOLVE the pointer once per read unit of work and hold it, so a query cannot straddle a promotion.
- **seeding** — creating a generation from a published artifact instead of backfilling from the node, which for a user-facing browser app is the PRIMARY path rather than a fallback: on a public node the backfill is frequently impossible, since old logs are not served at all. Two shapes, not equivalent: a captured **stream** (`captureStream` / `StreamFixture` / `replayStream`, which already returns an `ExistingStream`) seeds the stream, so later generations can still re-fold from it; a state **snapshot** (ADR-0028, `bootstrapFromSnapshot`) seeds the FOLD and reports a retention floor at its block, so a snapshot-seeded generation is a LEAF and cannot serve a later processor-only change.

## What must work FIRST

- **The COMBINED deployment is the milestone; the SPLIT is a deployment choice.** ADR-0003 divided the system into a **log-fetcher**, a **stream-builder**-plus-processor and a read surface, and every spec since is written per component, so the tree reads as though the split were the goal. It is not. The thing that must work end to end first is ONE process that follows a chain, folds into SQLite and answers HTTP, on any Node runtime — `work/specs/proposed/one-command-runs-the-whole-pipeline.md`, whose `run` command is exactly `fetch` plus `index` in one process via `createDirectIngestion` (that spec renamed the commands twice; `serve` now means ONLY the read-only tier, see the next bullet). Splitting is then a deployment decision an operator makes when the chain-facing host and the serving host genuinely differ, and it costs no rewrite because the transport is the only difference. The browser deployment is the other first-class target and is already reachable.
- **The COMMAND SET names deployment intents, not components** (`one-command-runs-the-whole-pipeline`): **`run`** follows the chain, folds and answers queries — the milestone and the default; **`build`** does the same but EXITS at the tip, producing a database or a publishable artifact; **`fetch`** is the chain-facing half, stateless, pushing to a remote; **`index`** is the folding half, receiving pushes and owning the database (it exposes `/ingest`, the WRITE path, and not the query API); **`serve`** answers queries over a database written elsewhere and writes nothing. Two compositions hold in the code rather than in prose: `run` IS `fetch` plus `index` plus `serve` in one process (the first pairing is `createDirectIngestion`), and `build` is `run` without the serving. Three naming rules worth keeping: `serve` means ONLY serving, because spending that verb on the all-in-one is what left the read tier unnameable; `index` is the FOLDING half, because the fetching half holds no cursor, no state and no database and so has the weakest claim to the project's central verb; and a split deployment is `index` plus `serve` against ONE database, which falls out of the set rather than needing explanation.
- **The QUERY LAYER is deferred, deliberately.** `/status` is the whole query surface for that milestone: today the reorg counters, the schema version, health and the last error, plus the CURSOR, which it does NOT report yet and which `one-command-runs-the-whole-pipeline` adds through a reporter injected beside `getDB` (the server has no store dependency, and the cursor is opaque behind the seam per ADR-0027). A richer layer is decided in principle (Hono, Yoga, Pothos over **entity declarations**, with `one-processor-everywhere` guaranteeing the schema source) and is NOT imminent. Several specs name it as their consumer; none of them should be read as evidence that it is being built.

## Server-side architecture terms

The server-side split (decided in `docs/adr/0003`-`0008`; partly built). "Processor" keeps the meaning defined above (`EventProcessor` / `JSObjectEventProcessor`, the reducer) and is NOT the name of a deployable.

- **log-fetcher** (`LogFetcher`, `@etherfold/core`) — stateless, chain-facing. Calls `eth_getLogs` and pushes contiguous block ranges of raw logs. Holds no cursor, no unconfirmed window, no reorg logic, so it can be restarted or replaced freely. One operation, `fetchAndPush()`; WHEN it runs belongs to a **fetcher host** (below), which is why it names no runtime and schedules nothing. Every chain call in a split deployment is here, including the `eth_chainId` check the chain-free receiver could never make. What it keeps between cycles is a HINT, not a cursor: the last `expectedFromBlock` the receiver reported, never persisted, dropped whenever a push fails, and corrected by a `409` — so losing it costs one request. Its transport is **`createHttpIngestion`** (same package), which maps status codes onto the two refusal families: `409` is resumable, the rest of the 4xx family is an `IngestionRefusedError` surfaced at once, a `5xx` or an unreachable server is an `IngestionUnavailableError` retried with bounded backoff.
- **a partial range is never pushed** — the sending rule of ADR-0004, and the most dangerous thing the log-fetcher can get wrong. A payload holds EVERY log in `[fromBlock, toBlock]`; truncation is expressed by LOWERING `toBlock`. An ANNOUNCED result cap shrinks the range (`RangeLogFetcher` reports how far it really got, as `toBlockUsed`); a SILENT one — exactly the cap back, no error — is treated as suspect rather than as an answer, so the range is halved until the count is under the cap, and a single block still landing on it is a `SuspectedTruncationError` and nothing is pushed. **The silent case is detected by matching the cap EXACTLY and cannot be detected otherwise**, since a capped answer and a complete one differ in nothing else: so `suspectResultCount` is a deployment's responsibility to set to its node's real cap (it defaults to 10000, the common one), and it is NOT `fetch.maxEventsPerFetch`, raising which widens the span asked for and makes truncation likelier. The reason is the receiver's inference: it cannot tell a short payload from "no logs there", so it would conclude an absence, and an absence is a reorg, and a reorg deletes state (the bug in `d24872f`).
- **fetcher host** (`@etherfold/fetcher-host`, plus `platforms/nodejs-fetcher`): the layer that decides WHEN a fetch cycle runs, which is the only platform-specific thing about fetching. The shared package holds everything that is not scheduling: the configuration a deployment supplies, the classification of a cycle into the five things a scheduler can act on (`progress` / `idle` / `contended` / `retry` / `fatal`), the wait after each, and the loop that drives them (`runFetcherLoop`). An adapter adds a runtime and nothing else, and must add nowhere to remember a block number. There is ONE schedule shape because driving the chain needs a host that can hold a PROCESS: a serverless trigger fires on a schedule rather than continuously and caps an invocation well below a first sync, which is why the serverless runtime here hosts the receiving half and not this one. Three of the five reports are not failures: `idle` (`up-to-date`) and `contended` (`yielded`) mean back off rather than alert, and only the ERROR's own `retryable` decides between `retry` and `fatal`. A host that re-derived that from a status code would retry a bad token forever. Distinct from the **log-fetcher** itself, which is the cycle; a host is the clock.
- **the wire is a deployment choice, not two implementations** (`createDirectIngestion` / `createHttpIngestion`, `@etherfold/core`): both sides of ADR-0004 are INTERFACES (`IngestionTarget` for the sender, `LogIngestion` for the receiver), so the same `LogFetcher` and the same `StreamBuilder` run split across a network or together in one deployable, with the transport as the only difference. `createDirectIngestion` is that second case in about eighteen lines: the receiver still owns the cursor, still derives every reorg and still refuses a batch that does not start where it says, because none of that came from HTTP. The one thing it must get right is that `UnexpectedFromBlockError` comes back as a CORRECTION rather than as a throw (the in-process `409`), recognised structurally so a second copy of the package cannot turn the resumable refusal into a crash. **Which shape goes where**: the COMBINED one is for a host that can hold a process (Node), where the network between the halves buys nothing; the SPLIT one is for a fetcher on such a host pushing to an indexer-server anywhere, including a Worker, which serves that half well. What is NOT a shape is a serverless fetcher of either kind, combined or fetch-only: a cron cannot follow a chain.
- **stream-builder** (`StreamBuilder`, `@etherfold/core`) — receives those ranges, is authoritative about where the next one must start (`expectedFromBlock`), derives reorgs, and will own the stored **emission stream** (append-only, retractions included; ADR-0006, not built yet, so today it drives an `EventProcessor` and stores no stream). Keyed by `{source, config}`. It is chain-free, which is the whole reason it is a separate object from `EthereumIndexer`: that class opens `load()` with `eth_chainId`, so the half of a split deployment that hosts the processor cannot use it. It reads the persisted cursor on every call rather than holding one, because an in-memory cursor is one serverless isolate's private opinion of a value the database owns. Distinct from a **wire batch** (`WireBatch`, the ADR-0004 envelope `{context, fromBlock, toBlock, latestBlock, logs}`): the batch is what crosses, the stream-builder is what receives it.
- **the cursor is the idempotency key** — the receiving rule of ADR-0004, and the reason the ingestion endpoint has no dedupe table and no idempotency header. A batch whose `fromBlock` is not the server's own `expectedFromBlock` is refused with `409` carrying that value (`UnexpectedFromBlockError`), and the sender re-sends from there; a batch re-sent after a lost acknowledgement fails exactly that check, so at-least-once on the wire becomes exactly-once in effect. `409` is the ONLY resumable refusal: a foreign `{source, config}` (`WireContextMismatchError`) or a malformed range (`InvalidBatchError`) is a `400`, because no block number makes it right. Note what the envelope deliberately lacks: no `complete` flag (completeness is an invariant, and truncation is a LOWER `toBlock`), no `removed` markers and no `unconfirmedBlocks` (the receiver derives every reorg, so that logic exists once).
- **reorg cause** (`ReorgCause`, `@etherfold/core`) — HOW a revert was concluded, and the two are never folded into one number. `contradiction` is proof (the same height now carries a different hash) and is ordinary chain activity; `absence` is an INFERENCE (a block we held is simply not in the re-delivered range) and is indistinguishable from a sender that under-delivered it. The server counts them separately in `Meta` and reports them on `/status` (`reorgs: {absence, contradiction, last}`), because a rising rate of the absence kind means truncation or misconfiguration, not the chain. It does not make the server unhealthy: it is a signal to investigate, not a fault.
- **indexer-server**: the deployable hosting the stream-builder plus an `EventProcessor`, owning the versioned state (keyed by `{source, config, processor}`) and serving both the state query API and the log feed. `@etherfold/server` is the platform-agnostic half of it (`/status`, `/admin/setup`, `/ingest`), with the database, the environment AND the stream-builder all injected; `platforms/*` are the hosts.
- **consumer**: anything reading the feed (a trigger/notification service). Independent, owns its own cursor, gate, outbox and delivery; the indexer-server stores nothing about it. Reserve "consumer" for this read side and never call it a watcher.
- **gate / lane**: the block bound a consumer applies before acting: `safe` (finalized) or `fast` (`latestBlock - N`, per chain, defaulting to `stream.finality`).

## Conventions

Standing per-change rules agents must follow in this repo.

- Changes that affect a published package's public API require a **changeset** (`.changeset/*.md`).
- **The code that exists is EVIDENCE, not AUTHORITY.** Read it to learn what is TRUE today; never to infer what must STAY. A shape in the tree records a decision someone made once, under constraints that may no longer hold, and it may also simply not work: reviewing the stream keeper turned up a mechanism (`streamNotYetSaved`, the unsaved-events carry-forward in `promiseToSave`) that reads as a safety net and NEVER FIRES, because the promise context it lives on is reset between cycles. So refactoring is the default rather than a licence to ask for: where an existing shape is in the way, change it, and delete what has stopped earning its keep, rather than building around it and leaving both. Nothing is published (above), so the cost of doing that is a changeset. What DOES constrain a task is its acceptance criteria, its scope fence and the ADRs it names — and a refactor that grows past the scope fence is a `## Decisions` note or a needs-attention signal, not something to smuggle in.
- **NOTHING IS PUBLISHED YET, so a breaking change costs a changeset and not a migration.** The `@etherfold/*` packages are not on npm (`work/tasks/backlog/publish-etherfold-and-deprecate-old-names.md`: "The rename landed in the tree; nothing has been published"), and the only consumers are repositories we own. So: do NOT contort a design to preserve a published type, do NOT add a compatibility shim for an external caller that does not exist, and do NOT let "this is breaking" outweigh "this is right" — delete the wrong thing rather than deprecating it beside the right one. Still WRITE the changeset, because the release that eventually happens needs the notes. This changes once the publish task lands, and this line is the thing to revisit then.
- **The blank sheet covers TYPES cheaply and BYTES ON DISK less cheaply, and the difference is a COST to weigh rather than a prohibition.** A type change costs a changeset. A PERSISTED-FORMAT change costs affected clients a RE-INDEX, and the price of that is entirely situational: trivial on a local node, and potentially IMPOSSIBLE on a public one, since old logs are frequently not served at all (which is the whole premise of `work/specs/proposed/a-generation-can-be-seeded-from-a-published-artifact.md`). So the question to ask is never "is this breaking" but **"what does re-indexing cost the people it lands on, and is a seed or snapshot available to them"**. Where a seed exists the answer is often "little, do it"; where none does, a migration earns its keep.

  **Today that set of people is EMPTY, and saying so plainly is what stops the question being asked wrongly.** Nothing is published, and the reference deployment has a live CONTRACT but no PLAYERS, so no disk anywhere holds state this project must preserve. Retrofitting it, if it ever mattered, is a re-index through the indexer-server plus a published snapshot and stream seed. So a MIGRATION is justified as PRODUCT CAPABILITY and not as debt owed to anyone: build one because an indexer whose upgrades do not blank the app is the thing being sold, not because a user is owed it. The corollary is the useful half: a one-time migration between two formats that only ever existed in UNRELEASED builds has no beneficiary at all and should be a SWEEP, not a data move. And note where the real capability lives — "an upgrade does not blank the app" is delivered by the GENERATION MODEL, not by keyspace migrations.
- **STRATAGEMS IS A CAPABILITY REFERENCE, NOT A COMPATIBILITY CONSTRAINT.** It exists to prove the system can do what a real launched game needs (a real ABI, real reorgs, 31,332 real logs, a shipped snapshot) and it is the honest yardstick for whether a design works. It is NOT a deployment whose stored bytes must be preserved: it can be retrofitted, re-seeded and re-deployed at will, because it is ours. Do not let it veto a better design, and do not cite "a launched game's users hold caches" as though it settled an argument — it does not, and treating it as a frozen production dependency would let an example dictate the architecture it exists to validate.
- Logging goes through **named-logs** (`import {logs} from 'named-logs'`), not `console.*`, in the core `@etherfold/core` package.
- A new ADR takes the next unused number and is named `NNNN-slug.md`. `pnpm check:adr` (`scripts/check-adr-numbers.mjs`, in the acceptance gate and in CI) refuses two ADRs claiming one number, because the number is a stable reference cited from source comments, `CONTEXT.md`, changesets and other ADRs. A GAP in the sequence is fine and not checked.
- Tests use **vitest**, in each package's `test/` folder; run via `pnpm --filter <pkg> test`.
- **`pnpm typecheck` is what checks `test/`.** Each package's build `tsconfig.json` includes `src/**/*.ts` only (it emits to `dist/`, so tests must stay out of it), and vitest strips types with esbuild without checking them. The per-package `tsconfig.typecheck.json` (`noEmit`, `rootDir: "."`, `include: ["**/*.ts"]` minus `node_modules`/`dist`) is the only thing that typechecks a test file. The include is deliberately the WHOLE package rather than a list of the directories that happen to hold code today, so a package-root config (`vitest.config.ts`, `playwright.config.ts`) or a new directory is covered without anyone remembering to widen a glob. **Run `pnpm build` first**: cross-package types resolve through each package's `dist/`, so `pnpm typecheck` on a clean clone reports missing modules. The acceptance gate already sequences them that way (`pnpm build && pnpm typecheck && pnpm test`).
